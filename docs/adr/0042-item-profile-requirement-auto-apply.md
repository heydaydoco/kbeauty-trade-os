# ADR-0042: §4.8 자동 적용 — 등록 트랜잭션 합류 + 활성 술어 사전 확인 멱등

- **상태**: 채택 (S2-2 계획 웹 세션 판정 2026-08-11 — 안건 ⑥ 기승인, PR-2 실장)
- **날짜**: 2026-08-12
- **관련**: DESIGN.md §4.8·§5.1·§17.1·[M2] 보강(S2-2 PR-2) / ADR-0021·0035(요건 세트 연결)·0037(활성 한정 유니크) / PROGRESS 부채 #15·관찰 "소급 3계열 비구현"

**맥락** — §4.8 "신규 등록 시 자동 적용"이 ADR-0021·0035로 두 번 이월돼 왔고, 적용 결과물(certifications)이 S2-2 PR-1로 섰다. 남은 판단은 실행 형태다: 트랜잭션 경계·멱등 수단·행위자.

**결정** — 신규 제품·SKU 등록 서비스가 flush 직후 같은 unit_of_work 안에서 apply_item_profile_requirements를 호출한다(§17.1 — 자동 적용 실패=등록 롤백, 테스트 실측). 대상 = 품목군 요건 세트 중 CONFIRMED + 적용단위 일치(제품→PRODUCT, SKU→SKU) 전건. 멱등 = 활성 한정 유니크 술어(ADR-0037)의 **사전 존재 확인**으로 생성 생략 — IntegrityError→422 변환 경로는 합류한 등록 트랜잭션을 오염시켜 쓸 수 없다. 생성 코어(_instantiate_template: 스냅샷 7필드+체크리스트 참조 복사+아웃박스)는 API 생성과 공유하고 상태 대입이 없다(층2 유지). 행위자 = 등록 조작자(created_by), 자동 표식은 created 이벤트 payload의 automatic(판정 ⑩ 대칭).

**근거** — 등록과 한 트랜잭션이어야 "등록됐는데 요건이 안 붙은" 중간 상태가 존재하지 않고, 사전 확인 멱등이어야 세션 오염 없이 전건 순회가 안전하다.

**기각한 대안** — 커밋 후 비동기 적용(중간 상태 창 + 디스패처 부재), create_certification 직접 호출(엔드포인트 멱등 키·422 변환·유니크 예외가 등록을 굴러뜨림 — 3중 장애), 소급 3계열 동시 구현(판정 문면 비포함 — 수동 경로 흡수), SET SKU 제외(문면에 없는 발명 — 수동 경로와 기준 상이해짐).

**되돌리기 비용** — 낮다. 훅 2곳(제품·SKU)을 제거하면 수동 등록 경로만 남고, 생성 코어는 API 생성이 그대로 쓴다.
