# ADR-0066: 오더 보드 — 비-Page 4열 뷰·벌크 3종은 건별 독립 트랜잭션·저장 필터는 DB·검색형 선택 컴포넌트는 S3-1 신규 화면 전부

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — D 묶음 D6, F 묶음 F16, 통합 X-52)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §3 ⑥·§7.4·§17.6·§18.4·§20 H·§2(원가 마스킹) / ADR-0027 / docs/plans/s3-1/design-D.md D6, design-F.md F16, design-integrated.md §1.4 X-52

**맥락** — §7.4는 "오더 보드(파이프라인 뷰+벌크 액션+저장 필터)"를 요구하지만 열·상한·벌크 범위·저장 위치가 없다. 프런트에는 `?size=200` 드롭다운이 여러 곳에 있고(200 초과 시 조용한 잘림) S3-1의 바이어·SKU·담당자·수임자 선택이 그 재발 트리거에 도달했다.

**결정** — ① **보드 범위는 접수 이후~확정까지**의 인테이크·SO 뷰만이며 할당·선적 열은 소비 세션이 붙인다(죽은 열 금지). `GET /order-board`는 **비-Page 단일 객체**(함수명 `get_order_board`, `list_` 접두 금지·최상위 배열 아님 — 기존 두 스캔 통과, 허용 목록을 만들지 않음)로 **고정 4열 `INTAKE_PENDING`·`SO_RECEIVED`·`SO_ON_HOLD`·`SO_CONFIRMED`**(열당 items ≤50+`total`+`has_more`)이고 `GET /order-board/items?stage=`가 Page 봉투로 드릴다운한다. 취소·거부는 보드에서 제외한다. 카드 필드에는 **원가·마진·매입가·여신·게이트 배지 필드가 응답 모델에 없다**(게이트를 카드마다 평가하면 N+1·낡은 판정 오독). 쿼리 수는 카드 수와 무관한 상수다. `BOARD_STAGE_STATUSES`(SO 상태→열) 상수+완전성 테스트("모든 SO 상태=매핑됨∪{CANCELLED}∪RESERVED")로 카드가 조용히 사라지는 일이 없다. ② **벌크는 `CONFIRM_INTAKE`·`CONFIRM_SO`·`ASSIGN` 3종**(대상 ≤50, 초과 422 `ORDER_BOARD.BULK.TOO_MANY`)이다. **원자성은 건별 독립 트랜잭션(§17.6)+결과 리포트**(부분 성공이 정상, 건별 `OK|SKIPPED|BLOCKED|CONFLICT|FORBIDDEN|FAILED`와 `blocked_gates`, 합계는 모든 건 커밋·롤백이 끝난 뒤 산출)이고 각 건은 **단일 통로 함수(`confirm_intake`·`confirm_sales_order`·`assign_*`)를 그대로 호출**한다(벌크 전용 확정 코드 금지 — 게이트·승인·소유권·권한이 개별과 동일). `CONFIRM_SO`는 override·승인을 부여·기안하지 않고 이미 개별로 부여된 유효분만 소비하며, 사유가 건별로 필요한 행위(보류·거부·취소·override·승인 요청)는 벌크에서 제외한다. 처리 순서는 id 오름차순(교착 방지), 건별 멱등 키는 `sha256("{bulk_key}|{action}|{kind}|{id}")` hex 64자(128자 한도 회피)라 같은 벌크 재요청은 건별 리플레이로 같은 리포트다. 권한은 TRADE·ADMIN이고 행별 서버 검증으로 권한 없는 행은 `FORBIDDEN` 리포트다. ③ **저장 필터는 DB**(`board_saved_filters`: `user_id`[`owner_user_id` 등 handover 감지 이름 금지]·`name`·`filter_config JSONB`, `unique_active(user_id, name)`, 사용자당 활성 20개, 본인 것만[타인 id는 404], 전 역할 사용 가능, `BoardFilter`는 `extra=forbid`로 저장·읽기 시 재검증하고 낡은 필터는 무시가 아니라 `needs_resave=true`)이며 기기 간 유실을 막는다(§7.4가 저장 필터를 보드 기능으로 명시). ④ **보드 CSV**(`GET /order-board/export.csv`)는 원가·마진·게이트·여신 열 없이 `render_csv` 통로·UTF-8 BOM·**최대 50,000행**(기존 `EXPORT_MAX_ROWS` 선례, 초과 422로 조건 좁히기 안내 — 조용한 잘라내기 금지)이고 audit 기록은 없다(선례). ⑤ **검색형 선택 컴포넌트 `SearchSelect`를 PR-3에서 신설**하고 이후 모든 PR의 화면이 사용한다: 서버 `?q=` 부분 일치(LIKE 와일드카드 이스케이프)+300ms 디바운스+`size<=20`+"결과 없음·더 있음" 표기이며, 서버 읽기 전용 확장은 `GET /partners?q&type`·`GET /skus?q`·`GET /users/lookup?q=`(ADR-0067)다. **S3-1 신규 화면(QT·PI·SO·PO·인테이크·보드·승인/대결)의 모든 거래처·SKU·담당자·수임자 선택은 이 컴포넌트 하나**이고 신규 프런트 파일에서 `size=200` 우회를 소스 스캔으로 금지하며, **기존 화면(products·skus·certifications 대상·TasksPanel 문서 연결)은 소급하지 않는다**(회귀 위험 대비 이득이 작고 관찰 트리거를 유지). 결과가 `total`보다 적으면 "더 있음·검색어를 더 입력"을 고지한다. ⑥ 프런트 신규 화면은 `/orders/board`·`/orders/intakes`·SO 상세 `GatePanel`이고 한국어 UI 규약(`break-keep`·헤더 nowrap·숫자 가운데)을 따른다.

**근거** — 열당 상한과 `has_more`·Page 드릴다운은 S2 인증 보드의 `TruncationNotice` 선례를 따른다. 기존 페이지네이션 스캔은 최상위 배열과 `list_` 접두 응답만 잡으므로 비-Page 객체+접두 금지로 충돌 없이 통과한다. 벌크를 건별 독립 TX로 두는 것은 §17.6이 요구하는 부분 성공과 §20 H "동시 20명 벌크 경합 정합"을 만족하기 위해서이며, 벌크 전용 확정 함수를 만들지 않으면 승인 우회 경로가 다중화되지 않는다(ADR-0053 차단표 #2). 검색형 선택은 PROGRESS의 드롭다운 4곳·"SKU 수백" 규모(§1)의 재발 트리거가 도달했기 때문이고, 소급은 이득이 작다.

**기각한 대안** — 벌크 HOLD·CANCEL(건별 사유 필요)·ASSIGN 제외 안, 벌크가 override·승인을 부여, 벌크를 하나의 트랜잭션으로(부분 성공 불가), 저장 필터를 브라우저 localStorage에, 보드 카드에 게이트 배지, 보드 CSV 5,000행 상한(기존 내보내기 6모듈이 50,000), 내보내기 audit(선례상 미기록), 열 상한 없는 전건 조회, 기존 화면까지 검색형 전환, 화면별 자체 선택기.

**되돌리기 비용** — 낮음. 벌크 액션 추가=열거+호출 1줄, 열 추가=상수 1줄(매핑 완전성 테스트가 강제), 저장 필터 테이블 제거는 개인 설정 소실뿐, 상한은 상수다.

**영향 세션** — S3-1 PR-3(`SearchSelect`·`q` 확장)·PR-15(보드·벌크·저장 필터) / S3-2·S4-2(보드 열 추가 — 상수+테스트) / 관찰 재판정: 벌크 HOLD·CANCEL·저장 필터 공유·게이트 배지 표시(배치 평가 비용 실측 후)·기존 화면 전환(200건 초과 실측 시).

**부기(2026-10-03 — S3-1 PR-15a 구현 확정, 같은 날 적대 검토 반영)** — (자율 확정 — 사후 번복 가능. 위 원문 결정은 고치지 않는다 — 아래 ⑦이 원문 두 문장의 의미를 좁힌다.) ① **보드 응답** = `{columns[4]{stage,label_ko,total,has_more,items≤50}, generated_at}`이고 쿼리 수는 상수 6이다(열 건수 2+열 카드 4, 카드마다 추가 질의 0). 6쿼리는 **한 스냅샷**(읽기 트랜잭션 첫 문장 `REPEATABLE READ, READ ONLY` — 드릴다운·CSV 동일)이라 쿼리 사이에 커밋된 확정이 같은 카드를 두 열에 싣지 않는다. 열 쿼리는 M12 부분 인덱스 3개가 받친다(q 부분 일치용 pg_trgm GIN은 부채 — 재판정 트리거: CONFIRMED SO 1만 건 또는 보드 p95 300ms). 카드 필드는 설계 목록에 `total_text`(판매 합계 표기 문자열)만 더했다. 인테이크 카드의 거래처명은 거래처 마스터(영문명 우선), SO 카드는 헤더 바이어 표기이고, `q`는 두 카드 모두 거래처 마스터 국문·영문명으로 찾으며 `IN-{숫자}`는 그 인테이크다. `age_days`=접수(생성)일부터 KST 날짜 차이. ② **벌크 멱등 두 층**: (a) **요청 지문**(액션·정규화·정렬한 대상(kind,id,version)·담당자)을 기존 멱등 인프라로 대조한다(스코프 `POST /api/v1/order-board/bulk`, 완료 기록 없음 — 지문 대조 전용). 같은 키+다른 지문은 **요청 전체 409 `COMMON.IDEMPOTENCY.KEY_CONFLICT`**(어떤 건도 실행하지 않는다). (b) 같은 지문이면 건별 파생 키로 진행한다: 확정 2종은 파생 키를 단일 통로에 그대로 넘기고(성공 재생·거부 키 미소비), **담당 지정의 단일 통로(PATCH)에는 멱등 키가 없으므로 벌크 모듈이 같은 트랜잭션에서 건별 claim/complete**(스코프 `…/bulk#ASSIGN`)한다 — 그래야 같은 키 재요청이 낡은 version CONFLICT가 아니라 최초 결과 재생이 된다. ③ **결과 매핑**은 판정 재수행 없이 코드·상태만 옮긴다: `TRADE_CHAIN.CONFIRM.GATE_BLOCKED`→BLOCKED(`blocked_gates`는 게이트·라인·수준·해소 방식·사유 코드·문구만 — basis·판정 해시·여신 수치는 싣지 않는다), **업무 거부 409**(`ORDER_INTAKE.LINE.STALE_MAPPING`·`TRADE_DOCS.DOCUMENT.DUPLICATE_BUYER_PO`·`ORDER_INTAKE.GATE.UNRESOLVED`·`APPROVALS.APPROVAL.STALE`·`TRADE_DOCS.COPY.SOURCE_NOT_ELIGIBLE`)→BLOCKED(`blocked_gates` 빈 목록 — `code`로 구분, 개별 처리 필요), 경합 409(`VERSION_CONFLICT`·`LOCK_BUSY`·`ORDER_INTAKE.STATE.NOT_PENDING`·`TRADE_DOCS.TRANSITION.NOT_ALLOWED`·`IDEMPOTENCY.KEY_CONFLICT`)·잠금 경합(55P03·40P01)·`StaleDataError`·분류표 밖 409→CONFLICT, 403·처리 도중 행위자 자격 상실→FORBIDDEN, 그 밖(404·422·예상 못 한 오류)→FAILED. 카탈로그의 409 전수가 시험으로 고정된다(새 409가 생기면 분류를 정하게 된다). ④ **더 엄격하게 정한 것**: 같은 대상이 다른 version으로 중복되면 422(설계는 '중복 제거'만 — 모호한 중복은 조용히 고르지 않는다), 벌크 담당자는 **활성+무역/관리자 보유**(ADR-0067 ③ — 단일 통로는 아직 활성만 본다: 부채, ADR-0067 부기), 액션·대상 종류 정합은 요청 스키마와 서비스 진입점 양쪽에서 검사하고 건 실행은 종류가 틀리면 멈춘다(fail-closed), **행위자 자격(활성·역할)은 건마다 DB에서 다시 읽는다**(처리 도중 권한 회수 TOCTOU — 상실 시 남은 건 미실행), 바깥 트랜잭션 안에서 벌크를 부르면 실행하지 않고 멈춘다(`in_unit_of_work` 가드), 요청 본문 상한 500(51~500건은 `TOO_MANY`, 그 위는 본문 검증 422). ⑤ **저장 필터**: 낡은 값은 `filter_config=null`+`needs_resave=true`(부분 적용·변환 없음). 20개 상한은 **사용자 단위 트랜잭션 advisory lock**(`pg_advisory_xact_lock(SAVED_FILTER_LOCK_NS, user_id)` — 스케줄러·시드 키 공간과 분리, 시험이 호출처·네임스페이스를 고정)을 잡은 **뒤 별도 문장으로 다시 세어** 지킨다 — 본인 행 `FOR UPDATE`는 행이 0개일 때 잠글 것이 없어 0개 상태 동시 21건이 전부 통과할 수 있었고, 잠금 문의 결과 행 수로 세면 READ COMMITTED에서 대기 중 커밋된 행이 빠진다(둘 다 실측). 이름은 strip **전** 원문에 보이지 않는 글자(Cc·Cf·Zl·Zp·한글 채움 — 공용 `app.core.text.invisible_char_problem`, 게이트 사유 판정과 같은 규칙)가 있으면 422이고, DB CHECK(`[[:cntrl:]]` — PG16은 C0·C1만 잡는다) 위반도 422로 번역한다. ⑥ **`GET /users/lookup`의 `q`·`assignee_target`은 추가만 했고 기본값은 종전(false — 활성 전원)**이다(ADR-0067 부기 2026-10-03). ⑦ **원문 두 문장의 의미 정정**: "처리 순서는 id 오름차순(교착 방지)" — 처리 순서의 목적은 **결정적 순서(재현성)**이고 교착 방지는 건별 독립 트랜잭션(건 사이에 잠금을 들고 있지 않다)과 각 단일 통로의 LOCK_ORDER가 맡는다. "같은 벌크 재요청은 건별 리플레이로 같은 리포트다" — 같은 키 재요청은 **OK·SKIPPED 건을 재생하고 거부 건(BLOCKED·CONFLICT·FAILED·FORBIDDEN)은 다시 실행한다**(단일 통로 규약: 거부는 키를 소비하지 않는다). 그 사이 상태가 그대로면 같은 리포트·새 확정·증거·이벤트 0이지만(시험 고정), 승인·override가 생겼으면 그 건은 이번에 통과할 수 있다 — "부작용 0"은 무조건이 아니다. **PR-15b 화면 계약**: 리포트는 `message_ko`를 먼저 보여 주고, BLOCKED는 상세 화면 링크·CONFLICT는 보드 새로 고침 안내다. 504·네트워크 오류 뒤에는 **같은 Idempotency-Key로 재전송해서 리포트를 회수**한다(같은 키는 완전히 같은 요청에만 쓴다). 근거: design-D.md D6·D7 / PROGRESS PR-15a 기록. **되돌리기 비용**: 낮음 — 지문 대조·건별 claim은 함수 1개씩, 매핑은 표 2개(경합·업무 거부 집합), 스냅샷은 문장 1개, advisory lock은 문장 1개, 엄격화 항목은 각 조건 1줄.
