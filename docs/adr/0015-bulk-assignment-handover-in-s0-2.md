# ADR-0015: 담당 일괄 이관 도구를 S0-2에 배정하고, 대상은 등록소로 강제한다

- **상태**: 채택
- **날짜**: 2026-07-27
- **관련**: DESIGN.md §2 권한·통제("담당 이관")·§20 H / WBS.md S0-2·S2-3 / WBS v1.3 / ADR-0012 / PROGRESS 부채 #10

**맥락** — §2는 "퇴사·휴가·담당 변경 시 담당 건(전표·인증·태스크·알림) 일괄 재배정 도구 + 계정 비활성 절차"를 요구하는데, 계정 비활성만 S0-2에 있었고 **재배정 도구는 어느 세션의 산출물에도 없었다**(ADR-0012로 담당자 라우팅을 배정하면서 발견). 배정처가 없는 항목은 아무도 만들지 않는다.

**결정** — 도구를 **S0-2**에 배정한다(담당자 컬럼이 생기는 시점이 곧 이관이 가능해지는 시점이다). 관리자 전용, **대상 전체가 단일 트랜잭션**(전부 아니면 0건), audit 기록 필수. 이관 대상은 `handover/targets.py`의 등록소가 유일한 출처이며, 담당자 컬럼을 가졌는데 등록되지 않은 모델이 있으면 아키텍처 테스트가 실패한다. §20 H의 "담당 일괄 이관 후 **라우팅 즉시 반영**" 완결 검증은 발송 채널이 서는 **S2-3**에서 한다.

**근거** — 부분 이관이 가장 위험하다. 태스크는 넘어갔는데 알림 수신자는 그대로면 사람은 "이관했다"고 믿고, 남은 건은 아무에게도 보이지 않은 채 기일을 넘긴다(§17.1 단일 트랜잭션). 대상 누락도 같은 형태로 조용하므로 사람의 기억이 아니라 기계가 잡아야 한다 — Phase 3의 전표·Phase 2의 인증이 담당자 컬럼을 추가할 때 등록소 한 줄을 강제받는다.

**기각한 대안** — ① Phase 3 이후로 미루기: 그때는 이미 담당 건이 쌓여 있고, 그 사이의 퇴사·휴가는 DB 직접 수정으로 처리하게 된다(감사 추적 밖). ② 테이블별 개별 이관 API: 호출자가 목록을 기억해야 하므로 누락이 구조적으로 보장된다. ③ 감사 컬럼(created_by_id 등)까지 이관: "누가 했는가"는 과거 사실이라 담당 변경으로 바뀌면 안 된다.

**되돌리기 비용** — 지금은 모듈 1개와 등록소 1개. 뒤집으면 이미 이관된 담당 이력의 되돌림 근거가 audit_log에만 남고, 이후 세션들이 등록소 없이 각자 이관 코드를 쓰게 된다.
