# ADR-0051: 전표 상태 기계 — 값·전이 25/101은 코드 고정·상태 대입은 단일 통로·상태이력 4표는 불변·이벤트는 생성+전이 전건

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — B 묶음 B1·B6·B8, 통합 X-17·X-21·X-24·X-25·X-49)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §2 ADR-11·§7.2·§17.1·§17.5 / ADR-0038(총수 고정·차단 3층)·0040(불변 이력 서식)·0041(죽은 열거 정의) / docs/plans/s3-1/design-B.md B1·B6·B8, design-integrated.md §1.2·§2.1(d)·§2.5

**맥락** — QT·PI·SO·PO 4종 전표가 처음 생기는 세션이라 상태 값·허용 전이·상태 대입 통로·이력·이벤트를 어긋남 없이 한 번에 고정해야 한다. 특히 §7.2에 PI·PO는 초안 상태가 없고, SO 후반 4값·PO 후반 3값은 소비 세션이 아직 없다. 판단할 것은 다섯이다: 상태 값과 전이 표, 자동 전이의 정의, 상태 대입 통로, 이력 저장, 이벤트 범위.

**결정** — ① **상태 값(코드 고정, VARCHAR(20)+`value_in` CHECK+StrEnum, `trade_docs/machine.py` 한 파일)**: QT 5(DRAFT·ISSUED·CONVERTED·EXPIRED·CANCELLED) / PI 5(ISSUED·PARTIALLY_PAID·PAID·EXPIRED·CANCELLED — **초안 없음**) / SO 8(RECEIVED·CONFIRMED·PARTIALLY_ALLOCATED·ALLOCATED·IN_SHIPMENT·COMPLETED·ON_HOLD·CANCELLED) / PO 6(ISSUED·SUPPLIER_CONFIRMED·PARTIALLY_RECEIVED·FULLY_RECEIVED·CLOSED·CANCELLED — **초안 없음**). ② **허용 전이 25방향(사람 15+자동 10)/미허용 101/총 126쌍**(QT 6[사람 3·자동 3]·PI 8[사람 1·자동 7]·SO 8[전부 사람]·PO 3[전부 사람]) — 총수는 EXPECTED 상수로 테스트가 고정한다. **SO 후반 4값(PARTIALLY_ALLOCATED·ALLOCATED·IN_SHIPMENT·COMPLETED)과 PO 후반 3값(PARTIALLY_RECEIVED·FULLY_RECEIVED·CLOSED)은 CHECK에만 싣고 엣지는 0(`machine.RESERVED`)**이다. ③ **자동 전이 = 대상 상태를 사람이 고르지 않고 규칙이 도출한 전이**(행위자는 NULL[스윕]이거나 유발자[입금 기록자·후속 전표 생성자]일 수 있다). QT의 ISSUED↔CONVERTED 연쇄와 ISSUED→EXPIRED, PI의 ISSUED→EXPIRED와 입금 수렴 6방향(ISSUED·PARTIALLY_PAID·PAID 상호)이 자동이고, 공개 API의 `to`로는 요청할 수 없다. PI 입금 수렴은 `converge_payment_status(session, pi_id, received_total_amount, due_amount, actor_user_id)` **단일 진입점**이며 `due_amount`는 컬럼이 아니라 호출자(S3-1 payments)가 `split_advance(PI.total, bp).advance`로 계산해 넘긴다(`advance_due_amount` 컬럼은 만들지 않는다). EXPIRED·CANCELLED PI에 입금이 오면 409 `TRADE_DOCS.PAYMENT.PI_NOT_OPEN`으로 fail-closed. ④ **SO 재개(ON_HOLD→RECEIVED|CONFIRMED)의 목표는 `confirmed_at`으로 판정**(NULL=RECEIVED, 아니면 CONFIRMED, 불일치 to는 409 `RESUME.TARGET_MISMATCH`)하며 재개는 게이트를 다시 평가하지 않는다. CANCELLED·SO→ON_HOLD는 사유(공백 제외 1~500자) 필수, EXPIRED는 서비스가 자동 문구를 남긴다. ⑤ **`status` 대입은 `trade_docs/transition.py`의 `record_birth`·`record_transition` 두 함수만** 한다(엣지 조회→RESERVED 거부→사유 검사→대입→이력 INSERT→아웃박스를 한 함수에서). 모델 생성자·`doc.status =`·`update().values(status=…)`·`setattr` 은 이 모듈 밖 0건(아키텍처 스캔+공회전 방지 자기검사), 쓰기 스키마에는 `status`가 구조적으로 없고 `extra=forbid`다. ⑥ **상태이력은 문서별 4표**(`quotation_status_log`·`proforma_invoice_status_log`·`sales_order_status_log`·`purchase_order_status_log`)이며 PkMixin+Base만·`IMMUTABLE_TABLES`+`revoke_mutations`. 열 `<doc>_id·occurred_at·from_status(NULL=탄생)·to_status·reason·actor_user_id(NULL=시스템)·automatic BOOLEAN NOT NULL`, **`automatic`은 actor NULL에서 파생하지 않고 명시 컬럼**(자동이어도 행위자가 있는 전이가 있다), `approval_id`는 SO 표에만 있고 승인 코어가 선 뒤의 **확정 배선 마이그레이션(M10)에서 ADD**한다. CHECK 6종(from/to 값·자기전이 금지·탄생 행·사유 필수·사유 길이·`actor_user_id IS NOT NULL OR automatic`)과 문서당 탄생 행 1개 부분 유니크를 둔다. ⑦ **이벤트는 생성+상태 전이 전건**(`quotations.quotation.created|status_changed` 등 4종×2, 사람·자동·연쇄 공히 `automatic` 표식), 같은 트랜잭션·`record_*` 안에서만 발행하고 payload는 화이트리스트 `doc_type(DocKind)·doc_id·doc_number·from_status·to_status·automatic·assignee_id·partner_id`(금액·사유·메모 금지 — 빌더가 `buyer_partner_id`·`supplier_partner_id`를 `partner_id`로 매핑). 전이별 개별 이벤트는 만들지 않는다. **전표 생성·전이·편집은 audit_log에 이중 기록하지 않는다**(상태이력 4표+아웃박스가 정본). ⑧ **전이 API**는 동결 액션 전용(QT `issue`·SO `confirm`)+범용 `POST /{docs}/{id}/transitions`(`to` Literal에서 동결·자동·RESERVED 엣지 제외)이고 생성·전이는 `Idempotency-Key` 필수, 전표 DELETE 엔드포인트는 없다.

**근거** — §7.2 문면 그대로(PI·PO는 "발행→"로 시작, QT만 '작성'이 있다)이며 ADR-0038의 총수 고정·사람/자동 구분 서식을 재사용한다(설계 B1). 후반 값을 CHECK에 미리 싣는 것은 후속 세션이 기존 테이블 CHECK를 수기 재정의하는 위험을 없애고, 엣지를 0으로 두는 것은 후속 흐름을 추측해 고정하지 않기 위해서다(ADR-0041 "죽은 열거" 정의는 DESIGN 근거·소비 세션이 없는 값이라 §7.2·WBS 근거가 있는 이 값들에는 해당하지 않는다 — 부기 참조). `VersionMixin`(`version_id_col`)이 ORM UPDATE마다 version을 올리므로 시스템 수렴도 version이 오르고 편집 중이던 사용자의 stale 저장은 409로 걸러진다(B8). 이력을 문서별로 나눈 것은 FK RESTRICT와 상태값 CHECK를 문서별로 정확히 표현하기 위해서이고(certification_status_log 계보), 대상 전표가 원장·분개를 만들지 않아 상태 전이 이력이 ADR-05 취소 세칙의 기록을 충족한다(ADR-0053). `converge_payment_status`의 호출자를 S3-1 payments로 확정한 것은 입금 사실 없이는 PI 게이트 테스트가 픽스처 조작이 되기 때문이다(ADR-0064).

**기각한 대안** — PI·PO에 DRAFT 추가(§7.2 문면 밖·WBS "§7.2 그대로"와 충돌), SO·PO 후반 엣지 36개를 지금 owner 라벨로 고정(후속 흐름의 추측), 다형 단일 이력 테이블(FK RESTRICT 불가·CHECK가 합집합으로 약화), `automatic`을 actor NULL에서 파생(입금 수렴·연쇄의 유발자 기록 소실), 상태 이력을 audit_log에 이중 기록, 전이별(confirmed·cancelled) 개별 이벤트(소비자 부재), 재개 목표를 최신 hold 이력 행으로 판정(DB CHECK로 "확정된 SO가 RECEIVED로 회귀"를 막을 수 없다), CONVERTED→CANCELLED 직접 엣지(후속을 먼저 취소하면 자동 복귀하므로 ISSUED→CANCELLED 하나로 충분 — 정의는 ADR-0052).

**되돌리기 비용** — 중간. 전이표·총수는 코드+테스트 상수라 엣지 추가는 낮다(ADR 부기+총수 갱신). PI·PO에 초안을 나중에 넣으려면 CHECK 재정의 마이그레이션과 동결 시점·생성 API 재정의가 따라와 중간~높음. 이력 표를 다형 1개로 통합하거나 컬럼을 바꾸는 것은 IMMUTABLE 테이블이라 새 마이그레이션+이관이 필요하므로 데이터가 쌓이기 전인 지금이 가장 싸다.

**영향 세션** — S3-1 PR-5~8(전이·이력·이벤트 구현)·PR-9/12(SO `approval_id` 배선, M10) / S3-2(SO 후반 엣지 추가·RESERVED 감소·총수 갱신·`CHILD_LINKS` 등록) / S3-3(입금 화면·`converge_payment_status` 확장) / S4-1(PO 후반 엣지) / S4-2(할당 상태 엣지·`AllocationPort` 실구현).
