# ADR-0058: 스케줄러 레지스트리 5잡 확장(7→12행) — 4금 논증·만료 스윕 규칙·"장부 확정"의 "전표"는 회계 전표로 한정

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — A 묶음 A14, B 묶음 B7, C 묶음 C7(잡), F 묶음 F18, 통합 X-45·§5)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §15(스케줄 레지스트리·자동화 4금)·§17.6·§21 / ADR-0013·0014(청소 배치 약속)·0038·0039·0044·0046·0050 / docs/plans/s3-1/design-A.md A14, design-B.md B7, design-C.md C7, design-F.md F18, design-integrated.md §2.6·§5

**맥락** — S3-1은 전표·승인·청소 관련 잡 5개를 `JOB_REGISTRY`에 더한다. 각 묶음이 "현 7행+1"로 8행을 적어 총수가 어긋났고(A의 `trade-docs-totals-verify`가 F 계산에서 빠져 11행이 됨), §15 L3 금지 문구 "장부 확정(분개·마감·**전표**·원장)"의 "전표"가 영업 전표와 용어가 충돌한다. 잡은 §15 4금(발주 확정·법적 판정·대외 발송·장부 확정) 밖이어야 한다.

**결정** — ① **레지스트리는 7행→12행**이다(기존 certification-sweep 06:00·outbox-dispatch interval@1·deadline-scan 06:30·daily-briefing 09:00·stagnation-scan 07:00·storage-monitor 05:00·backup-freshness 08:00에 아래 5행 추가, 시각 충돌 없음): `idempotency-purge` daily@04:20(F)·`session-purge` daily@04:25(F)·`trade-docs-totals-verify` daily@05:30(A)·`document-expiry-sweep` daily@06:10(B)·`approval-stagnation-scan` daily@07:10(C). 등록은 앱 경로(worker 기동 자동 등록·`register-jobs`)만이고 마이그레이션 시드는 금지다. `test_registered_jobs_stay_clear_of_the_four_bans`의 코드 집합·`test_scheduler_registry`·`e2e/test_scheduled_jobs`의 총수는 **잡을 추가하는 PR마다 그 PR에서 갱신**한다(집합 동일성 단정이라 미갱신은 CI 실패). ② **`document-expiry-sweep`**: 만드는 전이는 정확히 (QT,ISSUED→EXPIRED)·(PI,ISSUED→EXPIRED) 두 엣지뿐이다. 후보는 QT/PI `status='ISSUED' AND valid_until < 기준일(today_kst()) AND deleted_at IS NULL`이고 **후속(PI·SO)이 살아 있는 QT·PI는 제외**한다(PI에 SO가 생긴 뒤에는 입금이 계속 들어와야 하며 후속이 부모를 붙잡는다). 유효기간은 당일까지 유효(`valid_until < 기준일`일 때만 만료)이고 PARTIALLY_PAID·PAID는 상태로 이미 비대상이다. 건별 독립 트랜잭션(후보 수집→건마다 행 `FOR UPDATE`→상태·조건 재확인→`record_transition(EXPIRED, automatic=True, actor=None)`), 실패 건은 격리·계수하고 마지막에 잡을 FAILED로 표시하며 재실행 변화 0이다. **fail-closed 보강**: 후속 생성 가드(QT: ISSUED·CONVERTED 상태이고 `valid_until<today_kst()` / **PI: ISSUED일 때만**)는 스윕 실행 여부와 무관하게 422 `VALIDITY.EXPIRED`로 상태를 쓰지 않고 거절하며, QT 복귀·PI 입금 역기록 복귀 시 이미 경과했으면 같은 트랜잭션에서 EXPIRED로 추가 수렴(이력 2행), 파생 필드 `is_lapsed`는 계산값이다. 만료 임박(D-N) 알림은 만들지 않고 이벤트(`status_changed automatic=true`)로 `alert_rules` 구성이 가능하다. ③ **`trade-docs-totals-verify`**: 4헤더의 `total <> SUM(활성 라인 금액)`을 읽기 전용으로 검산해 ADMIN 인앱 알림(dedup `trade.totals_mismatch:{kind}:{id}:{KST일자}`, 본문에 doc_number만)을 만들고 **자동 보정은 하지 않는다**(예외는 잡 FAILED). ④ **`approval-stagnation-scan`**: REQUESTED 승인의 경과일 ≥ N(기본 2일, `alert_rules` event_type `approvals.stagnation`의 `config.days`가 덮어쓰며 형이 흐리면 기본값)이면 요청 알림과 같은 수신자 결정으로 독촉하고 dedup `approval:{id}:stagnation#{k}`(k=경과일÷N, N일마다 1건·소급 없음)이며 건별 독립 트랜잭션·실패 시 FAILED, **알림만 만들고 승인 상태·전표를 바꾸지 않는다**(잡·CLI는 `approvals.stagnation`만 임포트하고 `decide/consume/void/request`를 임포트하지 않는다). ⑤ **`idempotency-purge`·`session-purge`**(ADR-0013·0014 예약 이행): 술어는 기존 사용자별 청소와 동일(`expires_at <= now`, 유예 신설 없음), 1,000행 청크 반복 커밋, `idempotency.service.purge_expired_all`·`identity.service.purge_expired_sessions_all`이 자기 테이블을 소유하고 잡이 임포트하는 모델은 `IdempotencyKey`·`UserSession`뿐이다. 24h 이후 재시도는 키가 아니라 상태 검사(B 전이)가 이중 확정을 막는다. ⑥ **4금 논증**: 위 5잡은 (a) 발주·SO를 만들거나 바꾸지 않고 (b) 법적·규제 판정이 아니라 달력·산술 비교이며 (c) 대외 발송이 없고(아웃박스는 내부 라우팅·알림은 인앱) (d) 원장·분개·마감·채권을 만들지 않으며 (e) 승인 상태 부여 경로가 없다. **§15 L3 금지의 "장부 확정(분개·마감·전표·원장)"에서 "전표"는 회계 전표를 뜻하며 영업 문서(QT·PI·SO·PO — 원장·분개·채권을 만들지 않는다)는 해당하지 않는다**고 해소한다(DESIGN §15 부기). §15 자동화 레벨상 "기록만"(L3 허용 범위)이다.

**근거** — 만료를 계산값으로만 두면 목록·보드·필터의 저장 상태가 거짓이므로 스윕으로 저장 상태에 도달시키되(ADR-0039의 기각 논리), 돈이 걸린 상태·후속이 있는 문서는 제외해 입금 교착을 막는다. 전표가 처음 생기는 세션이 합계 이중망(저장 시점 검증+야간 검산)을 완성해야 §17.5·§21 문면이 성립한다. 승인 정체 스캔은 브리핑(09:00)의 "미확인 알림 집계"에 독촉분이 들어가야 하므로 기일 스캔 06:30·정체 스캔 07:00 뒤 07:10이다. 청소 잡은 백업 03:00·복원 리허설 일요일 04:00 뒤·storage-monitor 05:00 앞이며 S3-1이 확정·생성 API를 대량 추가하고 `response_body`에 PO 원가가 24h 저장되므로 이번에 이행한다. 잡 자체에서 유발하는 자동 정정은 조용한 보정이 되므로 알림만 둔다.

**기각한 대안** — 만료를 계산값만으로(저장 상태 거짓), 만료 알림·D-N 임박 알림(문면 근거 없음), PI의 후속 SO 보유 시에도 만료(입금 교착), 검산 불일치 자동 보정, 승인 만료·자동 결정, 정체 잡을 09:30(브리핑 이후)로, 청소 유예 기간 신설, 만료 스윕을 00:20에 두는 안(certification-sweep 06:00 뒤·deadline-scan 06:30 앞의 기존 순서 관용과 불일치), `Routing` 4번째 값.

**되돌리기 비용** — 낮음. 잡 1행·함수 1개라 폐기·시각 조정이 저렴하고 상태 표시·기술 행 삭제뿐이라 데이터 손상 위험이 없다. **PI의 후속 SO 제외 조건은 되돌리면 입금 교착이 재발하므로 유지 권장.** 임박 알림 추가는 가산이다.

**영향 세션** — S3-1 PR-5(검산 잡)·PR-6(만료 스윕)·PR-9(승인 정체)·PR-16(청소 잡·12행 총수 대사) / S3-2(기일 엔진에 QT/PI D-N 편입 판정) / runbook 잡 표.

**부기(2026-10-04 — S3-1 PR-16, 레지스트리 12행 대사 완료)** — ⑤의 청소 잡 2종이 들어가 `JOB_REGISTRY`가 **12행**이 됐고 `test_registered_jobs_stay_clear_of_the_four_bans`·`test_scheduler_registry`(총수 12·두 시각 단정·daily 시각 중복 없음)·`e2e/test_scheduled_jobs` 코드 집합을 같은 PR에서 갱신했다(X-45 종결). 잡 관리 **화면**은 없다(관리자 API `GET /api/v1/scheduled-jobs`만 — PROGRESS 부채). 청크 삭제는 `app/core/db/purge.py`의 `purge_in_batches`(1,000행·청크마다 독립 트랜잭션·기준 시각 호출 시작 시 고정·`RETURNING`으로 실삭제 수 계수)가 맡는다. **설계보다 좁힌 점(자율 확정 — 더 엄격한 쪽)**: 후보 행을 `FOR UPDATE SKIP LOCKED`로 집어 **지금 다른 트랜잭션이 잠근 행은 기다리지도 지우지도 않는다** — 진행 중인 멱등 claim의 이어받기(`claim()`의 행 잠금)·세션 `last_seen_at` 갱신과 겹쳐도 **청소 쪽은** 요청을 기다리지 않고 이어받는 행을 빼앗지 않으며, 남은 행은 다음 회차가 지운다(반대 방향 — 요청 경로의 사용자별 청소 DELETE는 SKIP LOCKED가 아니라 청소가 잠근 같은 액터 행에서 **최대 한 청크의 커밋 시간**만큼 기다릴 수 있다. 청크는 짧고 1,000행 상한이다). `purge_in_batches`는 열린 `unit_of_work` 안에서 부르면 거부한다(합류하면 전 청크가 한 트랜잭션으로 묶임 — 검토 반영). 실행 결과(`{"deleted": n}`)는 잡 반환값이며 `scheduled_jobs`에 결과 열이 없어 저장되지 않는다(실패만 FAILED+관리자 알림 — 기존 실행기 계약). 시험: `tests/integration/test_ttl_purge_jobs.py`(J — 경계 TTL 정확히·진행 중 claim·활성 세션·청크·재실행 0·실패 알림 / H — 동시 청소 4개·전역×로그인 청소 겹침) + 변이 9종 전원 kill.
