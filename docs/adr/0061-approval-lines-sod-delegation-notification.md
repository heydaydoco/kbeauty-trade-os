# ADR-0061: 결재선·SoD·대결·알림 — 결재선은 strict 초과·같은 통화만·요청 시점 동결, ADMIN도 자기 기안을 승인할 수 없다, 대결은 계산 유효성, 알림은 직접 notify와 결재함

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — C 묶음 C3·C4·C5·C7·C8, 통합 §4.8 오너 판정 후보 1순위)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §2(승인 워크플로우·L37 "관리자는 상시 통과")·§14 ⑭·§18.1·§20 H / ADR-07·11 / ADR-0012·0015·0018 ㉠·0045 / docs/plans/s3-1/design-C.md C3·C4·C5·C7·C8

**맥락** — §2는 "정(正)결재선=승인유형×금액임계→승인 역할 매핑 테이블(설정화), 승인자 부재 시 대결(기간·범위·이력)"이라고만 적었다. 선택 규칙(경계·통화·매핑 부재), 결재 자격과 직무분리(§2의 "관리자는 상시 통과"와 §20 H의 "승인 우회 차단[ADMIN 포함]" 층 충돌), 대결의 범위·중첩·종료, 승인 정체 알림이 비어 있다.

**결정** — ① **결재선(`approval_lines`)**: 1행=(유형·통화)에서 금액이 `threshold_amount`를 **초과(strict >)**하면 `approver_role`이 결재한다(임계 0=양의 금액 전부, 임계와 같은 금액은 한 단계 아래 구간). 선택은 단일 함수 `resolve_line`이며 후보=유형 일치∧**통화 정확히 일치(환산 없음)**∧`threshold_amount<amount` 중 임계 최대 1행이다. **매핑 없음은 fail-closed**로 요청 생성 불가 422 `APPROVALS.LINE.NOT_CONFIGURED`(approvals 행 0)이고, 자격자 집합이 공집합이면 422 `APPROVAL.NO_ELIGIBLE_APPROVER`다. 결재선을 바꿔도 진행 중 승인에는 소급하지 않으며 **요청 시점에 `required_role`·`approval_line_id`를 동결**한다. PATCH는 `approver_role`·`note`만 허용(유형·통화·임계는 삭제+신규)이고 유일성은 `(approval_type, threshold_currency, threshold_amount) WHERE deleted_at IS NULL`이다. **초기 행은 시드·CLI·앱 기본값 없이 ADMIN 결재선 관리 화면/API로만 공급**하며(등록 전 여신 초과 SO는 확정 불가 — 정상 fail-closed) 운영 개시 절차 1단계에 "결재선 등록(SO_CREDIT_EXCEEDED, 사용 통화별, 임계 0)"을 둔다. 임계 컬럼이 금액 접미라 **`ALLOWED_SENSITIVE_UNIQUE_KEYS`에 `("approval_lines","threshold_amount")`를 사유와 함께 등록**한다(ADR-0018 ㉠ 부기). ② **결재 자격**: 자격자=①활성 계정∧`required_role` 보유자 ②**활성 ADMIN 전원**(결재선 0행·역할 보유자 0명에도 결재가 영구 정체하지 않게) ③오늘(KST) 유효한 (유형·역할) 대결 수임자이고 모두 **요청자 본인 제외**다. **SoD는 예외 없이 "기안자≠결정자"이며 ADMIN도 자기 기안을 승인·반려할 수 없다**(403 `DECISION.SELF_APPROVAL`, 대결 경유는 수임자≠기안자∧위임자≠기안자, 그 밖의 무자격은 403 `DECISION.NOT_APPROVER`, 둘 다 `approvals.decision.denied` audit 후 커밋·예외). **§2 "상시 통과"는 접근 가드 층(엔드포인트 진입)이고 §20 H "승인 우회 차단"은 업무 게이트 층**이므로 충돌하지 않으며, **ADMIN도 CONSUMED로 전이할 APPROVED 행 없이 여신 초과 SO를 확정할 수 없다**(`force·override·admin` 파라미터가 시그니처에 없음을 AST로 고정). 자격 판정은 단일 함수 `decision_authority`와 그 SQL 조각을 결재함·`can_decide`·결정 API·알림 수신자가 공유한다. 결정 트랜잭션은 잠금 후 자격을 재계산한다(TOCTOU). VIEWER는 승인 API 전면 403이다. **1인 ADMIN 회사에서는 기안자가 유일한 자격자면 결정이 불가능한 것이 의도된 정상 동작**이고 해소책은 제2 결재 자격 계정이며 runbook에 명기한다 — 자기 승인 허용 모드는 **오너 판정 후보 1순위**로 PROGRESS에 등재한다. ③ **대결(`delegations`)**: 범위=(승인 유형 1개, 위임하는 결재 역할 1개)이며 금액 상한 컬럼은 없다(ADMIN 위임 시 전권 이양을 막고 새 승인 유형이 생겨도 기존 위임이 조용히 확장되지 않게). 위임자는 그 역할을 본인 자격으로 보유하거나 ADMIN이어야 하고(등록 시·결정 시 2회 검증), **재위임은 구조적으로 불가**(자격은 본인 역할 보유로만 인정)다. 기간은 KST 달력 날짜 양끝 포함, **소급 등록 금지**(`start_on>=today_kst()`), 같은 (위임자·유형·역할)에서 미종료 대결과 겹치면 409 `DELEGATION.OVERLAP`(위임자 users 행 `FOR UPDATE`로 직렬화)이며 **기간 수정 API는 없고** 조기 종료는 `POST …/revoke`(위임자 본인 또는 ADMIN)뿐이다. **유효성은 조회·결정 시점의 계산값**이다(`revoked_at IS NULL ∧ 기간 ∧ 위임자·수임자 활성 ∧ 위임자가 지금도 그 역할[또는 ADMIN] 보유 ∧ 수임자가 비조회 역할 보유` — 계정 비활성·역할 상실은 즉시 무효, identity→approvals 콜백 훅은 만들지 않으며 재활성 시 남은 기간이 있으면 다시 유효해지는 점은 수용하고 화면이 `ACTIVE|UPCOMING|EXPIRED|REVOKED|INERT`와 사유를 표시한다). 당사자·기간·범위는 컬럼 단위 UPDATE 권한으로 불변이고 사용 이력은 `approvals`·`approval_events`의 `decided_on_behalf_of_id`·`decided_delegation_id`이며 **대결 사용 시 위임자에게 알림 1건**을 보낸다. 수임자 선택 디렉터리는 `GET /approvals/delegation-candidates`(`{id, display_name}` 두 키뿐, ADR-0067의 `users/lookup`과 같은 조회 함수·스키마를 공유). ④ **알림·결재함**: 요청 알림은 아웃박스가 아니라 **`notify()` 직접 호출**(요청 트랜잭션 안에서 "승인 행이 있으면 알림도 있다")이며 수신자마다 `Routing.DEADLINE`+`assignee_id` 지정(수신자를 이미 활성으로 골라 넘기므로 폴백은 넘긴 뒤 비활성이 되는 경합에서만 ADMIN으로 관통, `alert_rules` 0행이어도 발송)이다. 수신자=`required_role` 보유 활성 사용자∪그 (유형·역할)의 유효 수임자−기안자, 공집합이면 활성 ADMIN 폴백(본문에 폴백 사유), 결과 통지는 기안자에게, 알림 본문·제목에 금액·이메일·원가를 싣지 않는다. **알림과 무관한 서버 계산 결재함**(`GET /approvals?scope=inbox|mine|all`·`inbox-count`)을 별도로 두어 알림이 없거나 늦어도 자격자에게 보인다. 정체 독촉은 `approval-stagnation-scan`(ADR-0058)이며 알림만 만든다. ⑤ **담당 이관 취급**: 승인 대기 건은 역할 기반이라 이관 대상이 아니며 승인 4테이블에는 ASSIGNMENT 이름 컬럼이 없고 handover에 등록하지 않는다(users FK는 이력·위임으로 분류).

**근거** — "임계 초과" 문면의 직독이 strict >이며 환율 규약이 미결인 상태에서 승인 라우팅이 환율 원천에 종속되면 다른 결정이 뒤집힐 때 함께 뒤집히므로 같은 통화만 비교한다(통화 결정·환산은 게이트 몫). 결재선 동결은 §2 "승인 후 불변"과 정합하고 ADMIN이 이미 모든 승인의 자격자라 "라우팅을 낮춰 우회"할 이득이 없다. 대결을 (유형+역할)로 한정하는 것은 ADMIN 위임 시 전 구간 권한 이양이라는 권한 초과를 막기 위해서다. 계산 유효성을 택한 것은 identity가 approvals를 임포트하지 않으므로 훅이 순환 임포트와 TOCTOU 창을 만들기 때문이며 계산 술어가 동등한 fail-closed를 이미 달성한다. `notify()`가 `assignee_id`가 활성이면 routing과 무관하게 그 사람에게 보내는 코어 동작을 활용해 `Routing` 3값(테스트 고정)을 늘리지 않는다.

**기각한 대안** — 임계 "이상"(경계 의미 반전 시 운영 데이터 재입력), 통화 환산 후 비교(환율 결정 종속), 결정 시점 재해소·진행 건 소급 적용(§2 위반), 결재선 시드·기본값, `approver_role` 유니크(동료 역할이 다른 구간에 재등장하는 정당한 조합 차단), ADMIN의 자기 승인 허용·"상시 통과"의 게이트 확대 적용, 대상 작성자≠결재자 SoD 확장(문면 근거 없음 — 관찰 등재), 유형만 범위인 대결·금액 상한 대결·90일 상한(문면 근거 없음)·identity 비활성 시 대결 자동 종료 훅, 승인 알림을 09:30에, `Routing` 4번째 값(역할 직접 지정), 지정 결재자 컬럼(handover 스캔 확장 동반).

**되돌리기 비용** — 낮음~중간. SoD 완화(ADMIN 자기 승인 허용)는 서비스 술어 1줄+`sod`·`on_behalf_not_requester` CHECK 재정의 마이그레이션+ADR 갱신이지만 §20 H를 약화하는 방향이라 **오너 명시 판정이 필요하며 이 결정이 사후 번복 가능성이 가장 높다**(1인 운영 현실). 환산 도입은 `resolve_line` 1함수+환율 계약 의존(스키마 무변경), 경계 반전은 함수 1줄이나 운영 데이터 재해석이 필요해 지금 확정한다. 다중 유형·금액 상한 대결은 nullable 컬럼 추가+유효 술어 확장(하위 호환)이다.

**영향 세션** — S3-1 PR-9(결재선·대결·알림·결재함 화면)·PR-12(요청·소비 배선) / 운영(runbook "S3-1 운영 개시": 결재선 등록·제2 결재 계정) / S3-4·S4(새 승인 유형의 결재선 등록 절차) / P6 헬스체크("결재선 미설정" 편입 관찰) / P7(Slack 결정도 같은 자격·SoD 적용).

**부기 (S3-1 PR-9a 구현, 자율 확정 2026-10-01)** — (위 원문 결정은 고치지 않는다.) ① **결재 자격의 단일 정의는 `approvals/authority.py`**: 결재함 술어(`eligibility_clause`)·`decision_authority`·알림 수신자·요청 시 자격자 공집합 검사가 같은 SQL 조각 `valid_delegations`와 같은 규칙을 쓴다(동등성은 무작위가 아니라 전수·경계 테스트로 고정). 결정 시점에는 `AuthenticatedUser.roles`를 믿지 않고 **승인 행 잠금 뒤 DB에서 역할·활성을 다시 읽는다**(`identity.active_roles_of` — 결정 중 비활성화되면 거부, 스레드 인터리브 테스트). 목록은 역할을 한 번만 읽어 넘긴다(N+1 방지, 쿼리 수 불변 테스트). ② **"오늘(KST)"의 단일 진입점은 `authority.kst_today()`** — 테스트가 이 함수를 고정해 경계일·UTC/KST 갈림(UTC 14일 15:30 = KST 15일 00:30)을 시험한다. ③ **대결 등록은 위임자 users 행을 `FOR NO KEY UPDATE`로 직렬화한다 — `FOR UPDATE`가 아니다**: 같은 트랜잭션이 앞서 멱등 행(`idempotency_keys.actor_user_id` FK)을 INSERT해 이 행에 `FOR KEY SHARE`를 쥐고 있어, `FOR UPDATE`는 동시 요청끼리 서로의 KEY SHARE를 기다리는 교착(40P01)이 된다(J 테스트가 실제로 재현·수정). ④ **알림**: 요청·독촉은 `Routing.DEADLINE`+수신자별 `assignee_id`(`alert_rules` 0행이어도 발송), 결과·대결 사용 통지는 `Routing.EVENT`(기안자·위임자 비활성이면 생략 — 폴백 없음), 기안자 본인이 한 행위(자기 회수·자기 편집에 의한 무효)는 알리지 않는다. 폴백 문구는 코어의 "규칙이 없어서"가 아니라 "결재 역할 보유자가 없어"다. ⑤ **정체 스캔**은 `approvals.stagnation`(알림만 — 승인 상태·이력 불변)이고 `approvals.service`를 전이적으로도 임포트하지 않는다(폐포 스캔 테스트) — 잡·CLI가 닿는 승인 모듈은 `stagnation` 하나뿐이다. N 기본 2일·`alert_rules.config.days` 덮어쓰기·형 흐림은 기본값·dedup 몫 k=경과일÷N(KST 달력일). ⑥ **임계 입력은 사람 표기 Decimal(≤15자리)이고 `core.money.parse_minor_amount`로 최소단위 변환**(자릿수 초과는 반올림 없이 422). 삭제 뒤 같은 임계 재등록은 부분 유니크라 신규로 성공한다.
