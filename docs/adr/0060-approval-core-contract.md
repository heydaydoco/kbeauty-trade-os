# ADR-0060: 승인 코어 — 유형은 코드 고정(S3-1은 SO_CREDIT_EXCEEDED 1종)·상태 6/전이 7·1회 소비와 무효화·승인 후 불변은 digest와 컬럼 단위 UPDATE 권한

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — C 묶음 C1·C2·C6·C8·X1~X3, 통합 X-07·X-22·X-29·X-30·X-31)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §2(승인 워크플로우)·§15·§16·§17.1·§17.5·§20 H / ADR-02·11 / ADR-0018 ㉠·0028·0038·0040·0041 / docs/plans/s3-1/design-C.md C1·C2·C6·C8·X1~X3, design-integrated.md §1.3·§2.1(e)

**맥락** — §2는 "기안→승인 2단, 승인 후 불변, 승인자 부재 시 대결"을 요구하지만 저장 골격·상태·소비 규약이 없고, §2가 든 승인 대상 6종 중 S3-1이 실소비하는 것은 여신 초과 수주뿐이다. 승인 결속 토큰을 C는 `digest`로, B·D는 `content_rev`로 각자 정의했고, 승인 소비(`consume`)가 확정 트랜잭션에 합류해 실행되므로 실패 시 기록을 남기는 방법도 정해야 한다.

**결정** — ① **승인 유형은 코드 고정 열거이고 매핑(금액 임계→역할)만 데이터**(ADR-11)다. S3-1이 값으로 두는 것은 **`SO_CREDIT_EXCEEDED` 1종**(`TYPE_TARGET`={SO_CREDIT_EXCEEDED: SALES_ORDER})이며 나머지 5종(임계 초과 비용·신규 파트너·권고 외 소싱·폐기·실사 차이)은 열거·CHECK·상수 어디에도 예약하지 않는다(ADR-0041). 유형 추가 절차는 열거·`TargetSpec` 등록·CHECK 재정의 마이그레이션(대상 컬럼 자동 대사)·소비 게이트 테스트다. ② **신규 4테이블**: `approval_lines`(Pk·Timestamp·SoftDelete·Version·Actor)·`approvals`(SoftDelete 없음)·`approval_events`(PkMixin+Base, IMMUTABLE)·`delegations`(SoftDelete 없음, 종료는 `revoked_at`). `approvals`·`delegations`·`approval_events`는 삭제 개념이 없어 SoftDelete를 두지 않는다(ADR-02 부기). `approvals`는 `target_type`(`SALES_ORDER`)·`target_id`(FK 없음 — 폴리모픽, 실재는 TargetSpec이 검증)·`target_label`·`status`·`requested_by_id`·`basis_amount/currency`(승인이 허용하는 금액 상한, >0)·`snapshot_digest CHAR(64)`·`snapshot JSONB`(표시용, 판정에 쓰지 않음)·`required_role`·`approval_line_id`·`decided_*`·`consumed_*`를 갖고, **활성 부분 유니크 `(approval_type, target_type, target_id) WHERE status IN ('REQUESTED','APPROVED')`**로 대상당 활성 승인 1건을 DB가 보증한다. 사유 컬럼은 두지 않고 `approval_events`가 단일 출처다(`actor_user_id NOT NULL` — 시스템 행위자 없음, `pair_allowed` CHECK가 허용 7쌍을 DB에서 다시 강제). ③ **상태 6값·전이 7방향**: REQUESTED·APPROVED·REJECTED·WITHDRAWN·CONSUMED·VOIDED, 종결 4태(REJECTED·WITHDRAWN·CONSUMED·VOIDED). 허용 7 = 사람 4(REQUESTED→APPROVED·REJECTED·WITHDRAWN, APPROVED→WITHDRAWN — `decide_approval`) + 도메인 통로 3(REQUESTED→VOIDED, APPROVED→CONSUMED·VOIDED — `consume_approval`·`void_for_target`), 미허용 29쌍(서로 다른 상태 순서쌍 23+자기전이 6)은 409 `APPROVALS.TRANSITION.NOT_ALLOWED`다. **재기안은 되돌림 전이가 아니라 신규 행**이고 **만료(시간 전이)는 없다**(승인 유효성은 소비 시점 재검증이 담보). REJECTED·WITHDRAWN은 사유 1~1000자 필수, VOIDED는 `reason_code`(`TARGET_CHANGED|TARGET_CANCELLED|CAP_EXCEEDED|NOT_REQUIRED`) 필수다. 상태 대입은 `_record_transition` 1곳뿐이고(상태 UPDATE+이벤트 INSERT+아웃박스가 한 함수·한 트랜잭션) 이벤트 6종은 `approvals.approval.requested|approved|rejected|withdrawn|voided|consumed`(id·유형·대상·from/to·행위자만, 금액·digest 없음)다. ④ **승인 후 불변 = 3층**: `approvals`의 스냅샷 컬럼(유형·대상·금액·digest·snapshot·required_role·approval_line_id·requested_by_id)은 **컬럼 단위 UPDATE 권한**(`restrict_update_columns` — `REVOKE UPDATE, DELETE, TRUNCATE`+허용 컬럼 `GRANT UPDATE`, `COLUMN_UPDATE_ALLOWLIST`: approvals·approval_lines·delegations)으로 INSERT 이후 불변이며(DB 트리거는 ADR-0028·0040 선례대로 미채택), `approval_events`는 IMMUTABLE, 대상 전표가 승인 상태에서 바뀌면 그 승인은 VOIDED(재승인 필요)다. ⑤ **결속 토큰은 digest 단일**이다: `sales_orders.service.gate_input_digest(session, so_id)`가 `sha256(canonical_json({buyer_partner_id, currency, fx_rate(str), fx_rate_date, lines:[[sku_id, quantity, unit_price_amount, is_free]…line_no순]}))`(정수 문자열·NFC, 골든 벡터 테스트, 메모·담당자·version 제외)를 만들고 C의 `TargetSpec.snapshot.digest`와 D의 `gate_evaluations.input_digest`가 공유한다. **`sales_orders.content_rev` 열은 만들지 않는다.** version 비교는 쓰지 않는다(라인만 바뀌고 부모 version이 안 오르는 S1-3 PR-3 결함 유형에 무력하고, 메모 수정 같은 무관 변경으로 재승인이 생겨 우회 압력이 된다). ⑥ **TargetSpec 레지스트리**: `TargetSpec(approval_type, target_type, consumer_module, snapshot(session, target_id, *, lock))`를 소비 모듈이 등록하고 소비 없는 spec은 금지(소비 접점 스캔은 소비 호출 PR과 같은 PR — PR-12). ⑦ **소비·무효·조회 함수**: `consume_approval(session, *, approval_type, target_id, actor_user_id) -> ConsumeResult(outcome: CONSUMED|NOT_REQUIRED|BLOCKED, approval_id, error)`는 확정 트랜잭션 **안에서** 호출되며 예외를 던지지 않고 결과를 돌려주고(중첩 UoW는 안쪽이 따로 커밋하지 않으므로 예외 시 VOID·감사까지 롤백된다) 호출자가 BLOCKED면 UoW를 정상 종료한 뒤 `raise result.error`한다. 순서는 `spec.snapshot(lock=True)`→`amount<=0`이면 VOID(NOT_REQUIRED)·NOT_REQUIRED→활성 APPROVED `FOR UPDATE`(없으면 `approvals.approval.bypass_blocked` audit 후 BLOCKED `APPROVAL.REQUIRED` 422)→digest·통화 불일치 VOID(TARGET_CHANGED)·`amount>basis_amount` VOID(CAP_EXCEEDED)→APPROVED→CONSUMED다. 통합에서 **`peek_active_approved(session, *, approval_type, target_id) -> ApprovalRef | None`**(읽기 전용 사전 조회 — 어떤 쓰기·VOID도 없음)을 추가해 clearance가 `approval_available`을 정하게 하고 승인은 미해소 시도에서 소비하지 않으며, **SO 취소·편집은 `void_for_target(session, *, approval_type, target_id, actor_user_id, reason_code)`**(REQUESTED·미소비 APPROVED→VOIDED, CONSUMED는 건드리지 않음)를 같은 트랜잭션에서 호출하고(B의 `withdraw_open_for_subject`는 폐기), 미해소 판정에서 "승인 필요·승인 없음"이면 `note_bypass_attempt(session, actor, target)`(audit 기록 후 커밋)를 BLOCKED 기록과 같은 커밋에서 호출한다. 무효화는 **eager 훅+lazy 백스톱**(결정·소비 시점의 digest·통화·상한·`gate_open` 재검증)을 둘 다 둔다. ⑧ **단일 결정 통로 `decide_approval(*, approval_id, actor, verb: APPROVE|REJECT|WITHDRAW, reason, version, idempotency_key)`**(actor는 항상 실 사용자, 우회·자동 표식 파라미터 없음)이며 **승인 요청 생성을 HTTP로 노출하지 않는다**(SO 엔드포인트 `POST /sales-orders/{id}/approval-requests`가 내부에서 `request_approval`을 호출 — 확정 시도의 부작용이 아니라 사람의 명시 두 번째 동작). 자동 승인 경로 부재는 4중으로 강제한다(`DECIDE_CALLERS` 소스 스캔·APPROVED 진입 1곳 AST·잡/CLI/seeds/imports/outbox의 상태 변경 함수 비임포트·`request/consume/void` 임포트 허용 집합). ⑨ **확정 거부 응답은 통합**된다: 미해소 게이트는 전부 409 `TRADE_CHAIN.CONFIRM.GATE_BLOCKED`이고(ADR-0063) `APPROVALS.APPROVAL.REQUIRED`(422)·`STALE`(409)는 **consume 시점 경합**(clearance 통과 후 승인 상태가 바뀜)에서만 발생한다. 승인 API는 VIEWER 전면 403이다. ⑩ 승인 4테이블은 담당 이관 대상이 아니다(역할 기반 — ASSIGNMENT 이름 컬럼을 두지 않고 `handover/targets.py`에 등록하지 않으며 users FK는 `USER_FK_CLASSIFICATION`의 이력·위임 분류로 면제 사유를 남긴다, ADR-0067).

**근거** — 소비 없는 유형 선확장은 "유형은 있는데 동작 없음"(ADR-0041 죽은 문)이다. CONSUMED를 불리언이 아니라 상태로 둔 것은 활성 유니크·결재함 필터·CHECK가 복합 조건이 되는 것을 피하기 위해서다. "승인 후 불변"은 결정 내용의 불변이지 소비 전 철회 금지가 아니므로 APPROVED→WITHDRAWN(잘못 내린 승인의 철회 통로)을 두되 원 결정 컬럼은 남는다. 컬럼 권한은 §17.5가 1순위로 든 "권한 제거" 수단이고 트리거를 기각한 이유(권한으로 충분한데 수단이 는다)와 같은 계보다. digest 단일화는 여러 묶음이 각자 정의하던 결속 토큰(`content_rev`·`digest`·`gate_input_digest`)이 서비스 카운터 훅 누락 시 fail-open이 되는 것을 막는다. `consume`이 결과 반환인 것은 중첩 UoW 계약(안쪽이 커밋하지 않음)상 "예외를 던지되 기록은 커밋"이 불가능하기 때문이다.

**기각한 대안** — 승인 유형 테이블·`approval_types`·5종 예약, `approvals`에 SoftDelete, 사유·상태를 approvals에 이중 저장, 승인 만료(자동 전이 표면), 종결 행 부활, `content_rev`(version 결속) 또는 서비스 카운터로 결속(훅 누락 fail-open·무관 변경 재승인), consume이 예외를 던지며 VOIDED 커밋(불가능), 스냅샷 불변을 BEFORE UPDATE 트리거로, 승인 요청 HTTP 생성 API·확정 시도가 승인을 자동 생성, 승인 결정 통로의 ADMIN 우회 파라미터, 다중 결정자·다단 결재(§1 BPM 금지).

**되돌리기 비용** — 낮음~중간. 유형 추가는 값+CHECK 재정의 1건, 상태 전이 추가는 machine 표+CHECK 재정의 1건+테스트 총수 갱신, digest 입력 집합 변경은 SO 함수 1개+테스트(기존 미소비 승인은 재요청). 컬럼 권한→트리거 교체는 마이그레이션 1건. `approvals`에 SoftDelete를 사후 추가하면 컬럼 추가+유니크 술어 재작성이라 중간. 승인 만료 도입은 additive.

**영향 세션** — S3-1 PR-9(승인 코어)·PR-11~12(게이트·확정 배선, 소비 접점 스캔) / S3-4(`EXPENSE_OVER_THRESHOLD` 유형 추가) / S4(폐기·실사 차이 유형) / P7(Slack 결정이 같은 `decide_approval`을 호출 — `DECIDE_CALLERS` 갱신+ADR) / S4-1(락 순서 규약은 ADR-0059가 승계) / WBS 배정 공백: 신규 파트너·권고 외 소싱 승인 유형의 소비 세션.

**부기 (S3-1 PR-9a 구현, 자율 확정 2026-10-01 — 승인 코어 백엔드 착지에서 확정한 세부)** — (위 원문 결정은 고치지 않는다.) ① **이력 `pair_allowed` CHECK는 `from_status IS NOT NULL` 가드를 둔다** — `(from IS NULL AND to='REQUESTED') OR (허용 7쌍)`만 쓰면 `from`이 NULL일 때 둘째 항이 NULL이 되어 CHECK가 통과한다(SQL의 NULL=위반 아님): `NULL→APPROVED` 같은 탄생 행이 들어가는 구멍이 실측 테스트에서 드러나 `(from IS NULL AND to='REQUESTED') OR (from IS NOT NULL AND (…))`로 확정했다(허용 쌍 SQL은 `machine.ALLOWED`에서 생성 — 이중 정의 없음). ② **`gate_input_digest`는 `sales_orders/digest.py`**(SO 모듈 소유, 계획 X-07)이고 PR-9a가 승인 코어와 함께 도입한다 — 입력 `{buyer_partner_id, currency, fx_rate(NUMERIC 고정 자릿수 문자열), fx_rate_date, lines:[[sku_id, quantity, unit_price_amount, is_free]…line_no순]}`의 canonical JSON(키 정렬·공백 없음·정수는 문자열·NFC) sha256이며 **골든 벡터 테스트가 직렬화 형식을 고정**한다(형식 변경 = 미소비 승인 전량 무효 → ADR 필요). ③ **TargetSpec은 `lock(session, id)`를 따로 두지 않고 `snapshot(…, lock)` 하나**다 — `lock=True`가 거래처→SO 순서로 잠근다. 그래서 반려·회수도 대상 잠금을 위해 `snapshot(lock=True)`를 부르되 **평가 불능 AppError는 삼킨다**(평가 불능이 철회·반려를 막지 않게). ④ **평가 불능(UNEVALUABLE) 전용 에러 코드는 없다**(통합 X-30이 `CREDIT_UNEVALUABLE`을 삭제) — spec이 `VALIDATION_INVALID_FIELD`(422, detail `credit`에 한국어 안내)를 던진다. ⑤ **요청은 `request_approval(session, *, approval_type, target_id, actor)`가 대상 잠금+스냅샷을 스스로 수행**하고(호출 트랜잭션에 합류), 같은 스냅샷의 활성 승인은 그대로 돌려주며(`created=False`) 스냅샷이 다르면 이전 승인을 VOID(TARGET_CHANGED) 후 신규를 만든다. 자격자 공집합이면 승인 행을 만든 뒤 422로 던져 **호출 트랜잭션이 롤백**된다(행·알림 0). ⑥ **`peek_active_approved`는 읽기 전용** — 상태·이력·버전을 바꾸지 않고(stale이어도 VOID하지 않는다) 권위 있는 판정·VOID는 `consume_approval`이 한다. ⑦ **소비 접점 스캔 부재 기록**: `consume_approval(` 호출·`request_approval` 엔드포인트·`void_for_target` 훅은 PR-12에 두고, 그 사이 `tests/architecture/test_approval_contract.py`의 `PENDING_CONSUMER_SCAN` 장부가 "spec은 있으나 소비자가 없다"를 코드로 기록한다(PR-12가 소비 호출을 더하면 항목을 지워야 테스트가 통과 — 스캔이 조용히 꺼진 채 남지 않는다). ⑧ **컬럼 UPDATE 허용 목록의 결합**: `restrict_update_columns`가 `COLUMN_UPDATE_ALLOWLIST`와 인자가 같은지 검사하므로 마이그레이션이 앱 상수를 임포트한다 — 허용 목록을 나중에 바꾸면 **옛 마이그레이션 재생이 ValueError**가 된다(변경은 새 마이그레이션이 자기 컬럼 목록으로 호출하는 방식이어야 함 — PROGRESS 관찰 등재).
