# ADR-0007: 에러 응답 봉투·코드 + 구조화 로깅·마스킹

- **상태**: 채택
- **날짜**: 2026-07-24
- **관련**: DESIGN.md §18.1·§18.4 / §20 K

**맥락** — §18.4의 "에러 메시지 이원화"와 §18.1·§20 K의 "로그 마스킹"을 실제로 구현하려면 봉투·코드 규칙과 마스킹 강제 지점이 필요한데 설계서에 정의가 없다.

**결정** — 에러 봉투 `{error:{code,message,detail,request_id}}`, 코드 `<도메인>.<대상>.<사유>` 3세그먼트. `AppError`가 detail(응답용)과 log_context(로그 전용)를 물리 분리(응답 직렬화 함수가 log_context 접근 경로를 갖지 않음). 마스킹은 structlog `redact_processor`가 `format_exc_info` 뒤·렌더러 직전에서 강제(키/값패턴/등록시크릿 3갈래). `capture_logs()` 사용 금지(체인 교체로 마스킹 우회).

**근거** — 봉투·코드는 30개 화면이 아니라 모든 엔드포인트+클라이언트가 공유하는 배포 후 불변 와이어 계약. 마스킹을 호출부 책임으로 두면 반드시 샌다. 순서가 뒤집히면 트레이스백 속 DSN 비밀번호가 조용히 통과하고 테스트는 초록으로 남는다(메타 테스트로 순서 고정).

**기각한 대안** — 화면별 자유 에러 형식(통일 불가) / 마스킹 호출부 책임(누락) / `capture_logs` 기반 마스킹 테스트("초록인데 평문" 거짓 안심).

**되돌리기 비용** — 봉투·코드 변경은 서버 전건 + 클라이언트 전건이 동시에 움직인다.
