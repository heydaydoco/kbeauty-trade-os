# ADR-0029: 파일 저장·서빙 보안 계약 — 서버 파일명·경로 밖 저장·attachment 고정·20MiB

- **상태**: 채택 (웹 세션 승인 조건 4의 구현 — 4항 전건)
- **날짜**: 2026-08-06
- **관련**: DESIGN.md §18.1·§2(백업 files/ 세트)·§20 K / WBS.md S1-3·S2-4 / ADR-0028

**맥락** — S1-3 PR-2가 리포 최초의 파일 업로드를 도입한다. 웹 세션 승인 조건 4가 보안 4항을 필수로 못박았고, §18.1(MIME·크기 검증, 실행 불가 경로, path traversal 차단, 다운로드 권한 검증)과 §20 K(업로드 실행 불가·경로 탈출 차단)가 상시 계약이다.

**결정** — ① **저장 파일명 = 서버 생성 uuid hex 32자.** 사용자 파일명은 표시·다운로드 헤더 전용으로 정규화(경로 조각 제거·제어문자 제거)해 따로 저장하고, 경로에는 절대 쓰지 않는다. DB CHECK(`stored_name_format`)가 형식을 이중으로 잠근다. ② **저장 루트 = 정적 서빙 경로 밖** — `FILE_STORAGE_ROOT`(named volume `/data/files`, nginx 루트·SPA 산출물과 무관)이고 접근 통로는 권한 검증 다운로드 엔드포인트 하나다. 단일 루트라 S2-4의 "pg_dump+files/ 세트 백업"이 그대로 선다. ③ **다운로드는 Content-Disposition: attachment 고정 + application/octet-stream + nosniff** — 신고된 MIME으로 서빙하지 않아 업로드물의 inline 렌더가 원천 불가하다. 허용 확장자 목록(.pdf·이미지·오피스·txt·csv·zip·ai)에 실행물(.exe·.sh·.js)과 인라인 렌더물(.html·.svg)이 없는 것이 이중 안전이다. ④ **크기 상한 = MAX_UPLOAD_BYTES 20MiB(명시 수치)** — Content-Length를 믿지 않고 스트림을 세며 초과 시 쓰다 만 실물을 지우고 413. 운영 nginx `client_max_body_size 25m`가 1차 방어선이고 앱 상한은 그 안쪽(멀티파트 오버헤드 여유)이다. 수치와 거부 동작은 테스트가 고정한다.

**기각한 대안** — 원본 파일명 저장(정규화해도 경로 결합 실수 한 번이 traversal — 원천 차단이 낫다), 정적 서빙+서명 URL(§18.1 "다운로드 권한 검증"과 어긋나고 세션 역할 검증을 우회), 신고 MIME 그대로 서빙(스토어드 XSS 통로), 해시 기반 내용 주소 저장(중복 실물 절약보다 삭제 시 참조 계수 복잡성이 크다 — S2-4 재검토 가능).

**되돌리기 비용** — 저장 규칙 변경은 기존 실물의 이관 스크립트가 필요해 중간. 상한·허용 목록 변경은 상수+테스트 한 쌍으로 낮다.
