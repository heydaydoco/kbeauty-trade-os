# ADR-0063: 게이트 공통 모델·원천·SO 확정 시퀀스 — 결과 4×해소 3·확정 시점 잠금 하 전건 재평가·미해소면 BLOCKED 커밋 후 409·PI 게이트 모드 의미

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — D 묶음 D3·D4·D5, E 묶음 E4·E6, 통합 X-11·X-26~X-28·X-30·X-34~X-36)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §7.3·§7.4·§7.10·§17.1·§17.2·§17.5·§20 A·H / ADR-05·11 / ADR-0017·0018·0024·0038·0041 / GC-C2·H1 / docs/plans/s3-1/design-D.md D3·D4·D5, design-E.md E4·E6, design-integrated.md §1.3·§2.10

**맥락** — §7.4는 게이트 6종(품번 매핑·단가 편차·시장 준비도·MOQ·중복 PO·여신)과 §7.3의 PI 입금 게이트를 나열할 뿐 결과값·해소 방식·평가 시점·증적 저장·확정 통로가 비어 있다. D와 E가 PI 게이트 의미(WARN=비차단 vs 차단)와 확정 오케스트레이션(거부 시 증적 행을 남기는가)을 정반대로 정의했다.

**결정** — ① **게이트는 하나의 공통 모듈 `gates`(도메인 무임포트, 평가기 등록부 주입)**로 표현한다. 결과 `GateLevel ∈ {PASS, WARN, BLOCK, UNKNOWN}`×해소 `GateResolution ∈ {NONE, OVERRIDE, APPROVAL}`이며 **UNKNOWN(평가 불능: 원천 부재·통화 불일치·설정 0행·예외)은 통과와 분리 표기하고 효과는 BLOCK과 동일(fail-closed)**이다. 미등록 평가기·평가 중 예외는 UNKNOWN(SAVEPOINT 안에서 잡되 55P03·40P01은 전파)이고, 확정 가능 판정은 단일 함수 `clearance`(PASS·WARN=통과, BLOCK·UNKNOWN은 NONE=미해소·OVERRIDE=유효 GRANT일 때만·APPROVAL=승인 가용일 때만 해소)뿐이며 통과 판정 로직의 복제는 금지된다. 게이트는 7종 `gate_code`(ITEM_MAPPING·DUPLICATE_PO·PRICE_DEVIATION·CREDIT·MARKET_READINESS·MOQ·PI_DEPOSIT)이고 명세 단일 출처는 `GATE_SPECS`다. ② **평가 시점**: 인테이크 검토는 저장 없는 실시간 계산(정보), **SO 확정은 거래처·SO 잠금 하 전건 재평가**(권위 — 화면·이전 결과를 재사용하지 않는다). 인테이크 확정의 하드 조건은 ITEM_MAPPING·DUPLICATE_PO·입력 완결성뿐이다. ③ **증적은 불변 2테이블**: `gate_evaluations`(확정 시도 전건, `outcome ∈ {CONFIRMED, BLOCKED}`, `results` JSONB[비PASS 결과·`passed_gates`·사용 override/승인 ref·`policy_source`], **`input_digest CHAR(64)`**[ADR-0060의 `gate_input_digest`, `content_rev` 아님], `UNIQUE(subject_type, subject_id) WHERE outcome='CONFIRMED'`로 SO당 확정 증거 1행)와 `gate_overrides`(override 가능 게이트 4종 PRICE_DEVIATION·MOQ·MARKET_READINESS·PI_DEPOSIT만 CHECK 열거 — ITEM_MAPPING·DUPLICATE_PO·CREDIT은 DB가 우회 불가를 강제, GRANT/REVOKE·사유 5~500자·`basis_hash` 결속, 유효성=`(subject, gate, line, basis_hash)`별 최신 행이 GRANT)이며 둘 다 IMMUTABLE+REVOKE다. SO에는 **DB가 게이트 없는 확정을 거부하는 데 필요한 3열(`credit_verdict`·`credit_approval_id`·`pi_gate_verdict`)만** 두고(ADR-0064) `pi_gate_override_reason`·`confirm_gate_snapshot`은 두지 않는다 — 상세 증적의 원천은 `gate_evaluations` 하나이며 SO 상세는 CONFIRMED 행을 조인한다. ④ **override는 별도 액션**(`POST /sales-orders/{id}/gate-overrides`+`…/revoke`, `Idempotency-Key`)이며 서버가 지금 평가해 대상이 BLOCK·UNKNOWN+`OVERRIDE`가 아니면 422 `NOT_APPLICABLE`·서버 해시≠요청 `basis_hash`면 409 `STALE`(판정 입력이 바뀌면 해시가 달라져 기존 override가 자동 무효)·역할 불허 403 `NOT_ALLOWED`이고 권한은 가격·MOQ=TRADE·ADMIN, **준비도·PI 입금=ADMIN**이다(확정 요청에 동봉하는 방식은 없다 — TRADE가 확정하고 ADMIN이 override하는 역할 분리 유지, 벌크도 부여하지 않는다). ⑤ **원천 규칙**: 품번은 `strip()` 후 정확 일치(활성 매핑 2쿼리·대소문자 다른 코드는 힌트만·자동 매칭·수동 SKU 지정 금지, 확정 시 저장본과 다르면 STALE_MAPPING), 단가 편차는 대칭 ±허용치의 **정수 교차곱** `abs(unit−ref)×10000 > tolerance_bps×ref`(정확히 허용치는 통과, Float 없음)이고 기준가는 인테이크 단계=`prices_at`·**SO 확정 단계=SO 라인 `list_price_amount`**이며 기준가 부재·통화 불일치(환산 없음)·`ref<=0`은 UNKNOWN이고 PURCHASE 조회는 0건, 시장 준비도는 `readiness.cells_for`(읽기 전용, 계산 규칙 1곳 재사용)로 GREEN→PASS·YELLOW→WARN·RED→BLOCK/OVERRIDE(ADMIN)·**GRAY→UNKNOWN**(통과로 읽지 않음)이며 응답에 "준비 상태 안내(법적 판정 아님)" `SCOPE_NOTE`를 동봉하고 판매 가능·적합 워딩을 금지한다, MOQ는 A의 `skus.moq`(NULL=PASS+안내·미만 BLOCK/OVERRIDE), 중복 PO는 `buyer_po_no_key`(NFKC→대문자→공백 제거, 구두점 보존, 제로폭 제거)로 다른 PENDING 인테이크·비취소 SO 점유 시 BLOCK/NONE(SO의 키 NULL은 WARN)이고 취소 SO·REJECTED 인테이크는 키를 점유하지 않으며 바이어 PO 개정판 전용 개념은 없다. DISCONTINUED SKU는 인테이크 단계 WARN·**확정 단계 BLOCK/NONE**이다. **CREDIT**은 E의 `evaluate_credit`를 감싼 어댑터로 EXCEEDED→`BLOCK/APPROVAL`·**UNEVALUABLE→`UNKNOWN/NONE`**(승인 경로 없이 확정 거부 — 금액을 모르면 승인 상한을 정할 수 없다)·WITHIN·NOT_MANAGED→PASS이며 여신 수치는 마스킹 비대상이다(ADR-0064). 정책은 `policy_settings` 단일(ADR-0065)이고 **D의 `gate_policies`는 삭제**한다. ⑥ **PI 입금 게이트**: 평가기 `payments.pi_gate.evaluate_pi_advance`가 `PI_DEPOSIT`의 평가기이며 **조건은 금액 대조**(`net_received >= split_advance(PI.total, bp).advance`, 등호 통과·`ZERO_REQUIRED` 통과, PI 상태값은 조건에 쓰지 않음)이고 **`TT_ADVANCE`일 때만 활성**(그 외 결제유형은 모드가 BLOCK이어도 NOT_APPLICABLE)이다. **PI를 참조한 SO는 PI의 결제조건·총액·통화 기준으로 판정**(`basis='PI'` — 확정 직전 결제유형을 바꿔 게이트를 끄는 우회 차단, 다르면 `terms_diverge=true`)하고 PI 없는 SO는 SO 자신의 조건이며 PI 없는 선수금 SO는 `PI_MISSING`이다(평가 불능≠통과). 비통과 사유는 `SHORT`·`PI_MISSING`·`PI_NOT_USABLE`이다. **모드 매핑(D 채택)**: 정책 `pi_advance_gate_mode` **OFF→PASS(`SKIPPED_OFF` 기록)·WARN→`WARN`(진행·비차단·기록)·BLOCK→`BLOCK/OVERRIDE(ADMIN)`**, 미설정=BLOCK(`policy_source=UNSET_DEFAULT`)이며 **E의 "WARN=차단·확정 본문 `pi_gate_override_reason`·BLOCK 우회 불가·`gate_overridden` 이벤트"는 삭제**한다(ADMIN은 어차피 정책 모드를 OFF로 바꿀 수 있어 "우회 불가" 주장이 실효가 없고 override는 D3의 별도 액션 하나다). `pi_gate_verdict ∈ {PASS, NOT_APPLICABLE, WARN, OVERRIDDEN, SKIPPED_OFF}`이며 override 부여·철회는 outbox `gates.override.granted|revoked`(id·gate_code·subject id뿐)로 감시된다. ⑦ **SO 확정 시퀀스(`trade_chain/confirm.py`, 사람 1클릭+`Idempotency-Key` 필수)**: (1) `idempotency.claim`(지문 `{so_id, version}`) (2) 무잠금으로 거래처·PI·QT id 조회 (3) `lock_buyer_for_credit`→`lock_chain`(QT→PI)→SO `FOR UPDATE`+version 대조·상태 RECEIVED 재확인 (4) 입력 완결성(`frozen_complete` → 422 `DOCUMENT.INCOMPLETE`, 롤백) (5) 게이트 7종을 **쓰기 없이 전건 평가** (6) `clearance`(유효 override+`peek_active_approved`) (7) **미해소면** CREDIT이 "승인 필요·승인 없음"일 때 `note_bypass_attempt` 후 `gate_evaluations(BLOCKED)` INSERT를 **예외 없이 커밋**(idempotency `complete` 안 함)하고 **409 `TRADE_CHAIN.CONFIRM.GATE_BLOCKED`**(`blocked_gates[]`에 게이트별 level·resolution·reason_code, 판매가·수량 값만) (8) **해소면** `consume_approval`(항상 호출, BLOCKED면 VOID·감사 커밋 후 raise `STALE`/`REQUIRED`) (9) `record_transition(RECEIVED→CONFIRMED, approval_id)`(`confirmed_at`·증적 3열 같은 flush)+QT 수렴+`AllocationPort.on_confirmed`(예외=전체 롤백)+`gate_evaluations(CONFIRMED)` (10) `complete(200, SalesOrderConfirmOut{sales_order, gates[], allocation, evaluation_id})`. **승인은 미해소 시도에서 소비하지 않고**, 승인 요청은 확정 시도가 만들지 않는 별도 사람 동작이며, ADMIN 분기·`force·override·bypass` 인자는 없다. 미해소 게이트는 전부 `GATE_BLOCKED`(409) 하나로 통합되고(E의 `TRADE_DOCS.GATE.*` 2종·D의 `TRADE_CHAIN.CONFIRM.APPROVAL_REQUIRED` 삭제) 여신 조회는 `/gates`가 CREDIT 항목의 `basis`+`advisory:true`로 흡수한다(`credit-check` 삭제). 후속 체인의 S3-1 완결 몫은 SO CONFIRMED 전이+`status_changed` 이벤트까지이며 포트·스텁·비활성 버튼을 두지 않는다(할당·선적 계획·서류 태스크는 각 세션의 사람 1클릭). ⑧ **자동 확정 경로 부재**를 한 파일 `test_no_auto_confirm_code_path_exists`에 엔트리 등록 방식으로 고정한다(인테이크 확정·SO 확정·PO 생성·QT 발행·승인 결정/소비/무효/요청·벌크 — 각 묶음이 (보호 함수, 허용 호출처, 금지 임포트)를 1행씩 등록).

**근거** — 게이트를 한 모델로 세우면 S5-1 채널 리스팅 게이트(GC-C2)가 그대로 재사용한다. UNKNOWN을 통과와 분리하고 BLOCK과 같은 효과로 두는 것이 "평가 불능을 통과로 취급 금지"(fail-closed·fail-visible)다. 확정 시점 재평가는 §17.2 확인→기록 창과 S1-3 PR-3의 "확정 시점 재검증 부재"의 재발 방지이며, 스테이징 결과를 신뢰하지 않는다(TOCTOU). override와 확정의 권한이 다를 수 있어(ADMIN vs TRADE) 동봉 방식은 역할 분리를 깬다. BLOCKED 증적 커밋은 승인 소비와 같은 트랜잭션에 섞이면 승인이 사라지므로 게이트 전건 평가가 소비보다 먼저다(승인 조회·소비를 2단으로 분리). WARN을 비차단으로 둔 것은 §7.3 "경고/차단 설정"의 통상 의미이고 진행을 막아야 할 사안은 BLOCK으로 올린다. 기준가를 SO 라인 `list_price_amount`로 잡는 것은 mutable한 `sku_prices`를 확정 시 다시 읽지 않고 "당시 기준가 대비"를 재현하기 위해서다.

**기각한 대안** — 게이트별 결과값 체계·확정 서비스 내 분산 판정, 스테이징 결과를 SO 열 캐시로 저장, 게이트 결과를 SO 열 스냅샷(A·B 분류표 결합), UNKNOWN=PASS, WARN=ACK 필요/차단, override를 확정 요청에 동봉, PI 게이트를 PI 상태값으로 판정, SO 자신의 결제조건으로 판정, 기준가를 QT 참조로, 통화 불일치 환산, 준비도 GRAY=PASS, MOQ NULL=UNKNOWN, 승인 소비를 게이트 평가보다 먼저·BLOCKED 기록을 롤백 위치로, 확정 거부를 멱등 결과로 기록, 확정 시도가 승인을 자동 생성.

**되돌리기 비용** — 중간. `resolution`/역할 배정은 상수 1곳+테스트(낮음), 확정 순서 재배치는 함수 1개 안이지만 **테이블은 S3-2 이후 소비가 시작되면 이관이 필요해 첫 PR 전에 확정**한다. 결과 저장을 SO 열로 옮기는 것은 A·B 분류표 재작업이라 비싸다. 정규화 규칙 변경은 `buyer_po_no_key` 재계산 마이그레이션(데이터가 초기라 저렴)이다.

**영향 세션** — S3-1 PR-11(게이트)·PR-12(확정 배선)·PR-13(인테이크 하드 게이트) / S3-2(SO 확정 이벤트 소비·선적 계획 초안) / S3-3(PI 기본 모드 WARN→BLOCK 전환은 payments 이후 오너 결정) / S4-2(할당·백오더 분기) / S5-1(`subject_type`·`gate_code` CHECK 확장·자체 평가기 등록) / S5-4(조건부 자동 확정 ADR이 자동 확정 부재 테스트 개정).
