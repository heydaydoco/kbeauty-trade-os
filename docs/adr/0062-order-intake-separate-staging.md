# ADR-0062: 오더 인테이크 — 오더 도메인의 물리 입구는 별도 order_intakes 2테이블·SO 접수는 인테이크 확정의 산출물(2단 흐름)·착지 단일 통로·원본 파일 미보관

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — D 묶음 D1·D2·D5(인테이크), 통합 X-13)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §3 M9·§7.2·§7.4·§12.1·§12.2·§17.4·§17.5 / ADR-09(스테이징 원칙)·08(AI 무예외 사람 확정) / ADR-0027·0030·0038·0041 / docs/plans/s3-1/design-D.md D1·D2·D5, design-integrated.md §1.1 X-13·§2.1(f)

**맥락** — 바이어 PO(수동·CSV)를 받는 입구가 필요한데 §7.4의 "스테이징 한 입구"와 §7.2의 SO 첫 상태 "접수(스테이징)"를 구현하려면 `import_staging`(마스터 왕복 diff 전용: 행 불변·원자 확정·파일 미보관·ID 키 diff)을 확장할지 별도 저장소를 둘지 정해야 한다.

**결정** — ① **오더 도메인의 물리 입구는 별도 모듈 `order_intake`의 2테이블 `order_intakes`·`order_intake_lines`**이고 `import_staging`은 마스터 왕복 전용으로 유지한다. "스테이징 한 입구"는 **원칙**(파서·AI·엑셀·채널→사람 검토→확정, 파일 해시+문서번호 멱등)이며, **SO '접수'(RECEIVED)는 인테이크 확정의 산출물**이다(2단: 인테이크 PENDING→[사람 1클릭 `confirm_intake`]→SO RECEIVED→[게이트·승인 후 사람 1클릭 확정]→SO CONFIRMED). ADR-09·§12.2 원문은 고치지 않고 DESIGN §7.2·§12.2·§3 M9에 부기한다. ② **상태 3값 PENDING/CONFIRMED/REJECTED, 허용 2(PENDING→CONFIRMED·PENDING→REJECTED[사유 ≥5자])·미허용 4, 자동 전이 0**이며 종결 탈출 0이다. 상태 대입은 `apply_intake_transition` 1곳뿐이고 생성·PATCH 스키마에는 `status`·`sales_order_id`·`decided_*`·`source_*`·`buyer_po_no_key`가 구조적으로 없다(`extra=forbid`). **삭제 엔드포인트가 없고 폐기는 REJECT**(행·스냅샷·사유 영구 보존 — §12.1 "거부 이력 보존")다. ③ **불변 필드**: `extracted_snapshot`(원본 JSONB)·`source_kind`·`source_sha256`·`source_group_key`·`original_filename`·`buyer_partner_id`·`currency`는 등록 후 변경 불가이고 강제는 DB CHECK(쌍 규칙)+ORM `before_update` 가드+Core `update()` AST 스캔의 3층이다(트리거 미채택 — ADR-0028·0040). 수정 이력 테이블은 두지 않고 원본 스냅샷 대 현재 값 diff로 §12.1 목적을 충족한다. 백링크는 인테이크→SO 한 방향(`sales_order_id`)이며 SO 쪽 역FK는 없다. 재접수(복제)를 위해 **`order_intakes.copied_from_so_id`**(같은 바이어·CANCELLED SO)를 두고 `confirm_intake`가 `sales_orders.copied_from_id`로 복사한다(ADR-0052). 결제조건·Incoterms·환율은 인테이크에 싣지 않는다(SO 접수 후 SO 편집에서 입력, `frozen_complete`가 확정 시 강제 — 부분 복사는 SO의 형태 CHECK 위반이다). ④ **착지 단일 통로 `register_intake(...)`**는 `status` 인자가 없어 항상 PENDING으로만 착지하고 라우터·파서가 `OrderIntake`를 직접 생성하지 않는다(AST). **입구는 2종(MANUAL·CSV)**이며 수동 폼 본문에는 `sku_id` 입력 필드가 없다(품번 매핑 우회 금지 — 서버가 `resolve_buyer_items`로 해석한 결과만 저장). **CSV 표준 양식**은 UTF-8-SIG·헤더 1행 완전 일치·9열(`바이어코드|바이어PO번호|PO일자|통화|목적지시장코드|바이어품번|수량|단가|요청납기일`)·1행=1라인이고 그룹 키=(바이어코드, `buyer_po_no_key`)이며, 날짜는 ISO `YYYY-MM-DD`만·수량은 정수(천단위 콤마는 위치가 맞을 때만)·단가는 통화 최소단위 자릿수 이내(초과 반올림 없이 오류)·코드 셀의 엑셀 지수표기는 행 오류·`.xlsx`/`.xls` 미수용(전용 안내 422)으로 **추측 변환을 하지 않는다**. **원자성은 파일 전체**(모든 오류를 한 번에 리포트, 하나라도 오류면 착지 0건)이고 **품번 미매핑만 오류가 아니라 `sku_id NULL`로 착지**해 검토 화면이 등록을 유도한다. 상한은 20 MiB·50,000행·파일당 그룹 200·그룹당 라인 200(인테이크당 라인 상한 200)이다. **파일 해시 멱등**은 `(source_sha256, source_group_key) WHERE status='PENDING'` 부분 유니크(확정·거부 후 재업로드는 PO 중복 검사가 수렴)이고 중복 바이어 PO 진행 중 차단은 `(buyer_partner_id, buyer_po_no_key) WHERE status='PENDING'`이다(ADR-0063). ⑤ **`confirm_intake` 한 트랜잭션**: 멱등 claim→인테이크 `FOR UPDATE`→입력 완결성(422: BUYER 재확인·시장·통화·라인≥1·**같은 SKU 유상 라인 중복 `DUPLICATE_SKU`**·금액 상한)→하드 게이트 재평가(전 라인 재해석 — 미매핑·삭제 422 `UNMAPPED_ITEMS`·저장본과 다르면 409 `STALE_MAPPING`·DUPLICATE_PO 409)→`create_received_sales_order`(SO 접수 생성, 채번은 트랜잭션 마지막, `price_basis='BUYER_PO'`·`list_price_amount` 스냅샷)→`apply_intake_transition(CONFIRMED)`→이벤트→`complete`이며 **PRICE·MOQ·MARKET·CREDIT·PI 게이트는 접수를 막지 않는다**(확정 시점 판정). ⑥ **자동 확정 부재**: 어떤 입구도 PENDING으로만 착지하고 CONFIRMED로 가는 유일 경로는 사람 1클릭이며 ADR-09의 "결정적 파서 조건부 자동 확정 예외"는 S5-4 소비이므로 S3-1은 구현하지 않고 부재를 아키텍처 테스트로 고정한다(S5-4는 ADR로 테스트를 개정). ⑦ **원본 파일은 S3-1에서 보관하지 않는다**(`extracted_snapshot`+`source_sha256`+`original_filename`으로 출처 특정) — `documents.owner_type='ORDER_INTAKE'`(12자 ≤13)·`order_intakes.document_id` nullable 추가형은 소비 세션(S6-1)의 예약 값으로만 명기한다. ⑧ `ASSIGNMENT_TARGETS`에 `AssignmentTarget("order_intakes", …)`(**label=테이블명**)를 등록한다.

**근거** — `import_staging` 불변식(행 불변·원자 확정·파일 미보관·ID 키 diff)과의 충돌 때문에 확장 안과 SO 겸용 안은 3안 일치로 기각됐다. §12.1의 "거부·수정 이력 보존" 목적(파서·프롬프트 개선 데이터)은 원본 스냅샷과 현재 값 순 diff로 충족되고 편집 단위 로그는 문면 근거가 없다. 부분 착지 후 수정본 재업로드는 sha256이 달라 이미 착지된 오더와 PO 중복으로 충돌하므로 파일 전체 원자가 옳다. 파일 1개=오더 N건이라 `unique_active(owner_type, owner_id, sha256)`에 맞추려면 인테이크마다 같은 파일을 복제 보관해야 해 documents 연동을 소비자가 생길 때까지 미룬다(ADR-0041). `confirm_intake`가 잠금 하에서 전 라인을 재해석하는 것은 §17.2 "확인→기록" 창 방어다.

**기각한 대안** — `import_staging` 확장·SO를 스테이징 겸용, 수정 이력(`edit_log`) 테이블, 거래처 미등록 상태 착지(`buyer_partner_id` NULL — AI 경로 소비 시 재판정), CSV 그룹별 부분 성공, 소스 열거에 AI·이메일·채널 선반영(죽은 열거), 헤더 안내 행이 든 템플릿(완전 일치 파서가 오류 처리), 엑셀 일련번호·모호 날짜 추측 변환, 무상(0원) 라인 인테이크 수용(SO 접수 후 A 규칙으로), 품번 SKU 수동 지정(매핑 게이트 우회), 원본 파일 즉시 보관.

**되돌리기 비용** — 중간. 마이그레이션 전은 낮고, 테이블 생성 후 시안 A(`import_staging` 확장)로 전환하려면 데이터 이관+CHECK 3종 재정의가 필요해 그 방향이 더 비싸다. 소스·상태 값 추가는 CHECK 재정의 1건, 백링크 방향 변경은 컬럼 이동 1건, CSV 양식 열 추가는 헤더 상수+파서 1곳(공지 필요)이다.

**영향 세션** — S3-1 PR-13(인테이크 MANUAL)·PR-14(CSV)·PR-15(보드 벌크가 같은 확정 통로를 건별 호출) / S5-4(조건부 자동 확정 ADR·`source_kind` 확장) / S6-1(AI PDF 경로의 `source_kind`·원본 문서 연결·거래처 NULL 착지 재판정) / DESIGN §7.2·§12.2·§3 M9 부기.
