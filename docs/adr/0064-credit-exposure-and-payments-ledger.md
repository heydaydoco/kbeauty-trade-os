# ADR-0064: 여신·입금 — 노출 산식은 가장 좁은 안전 결정·여신은 마스킹 비대상 유지·payments 입금 원장이 S3-3의 정본·SO 증적 3열·한도 변경은 ADMIN

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — E 묶음 E1·E2·E5·E7·E9, 통합 X-11·X-21·X-32·X-33)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §2·§3 표 맵(`payments`)·§4.6·§7.3·§7.10·§17.2·§17.5·§20 A·H / ADR-05 / ADR-0003·0018·0026·0040·0048 / docs/plans/s3-1/design-E.md E1·E2·E5·E7·E9·E11, design-integrated.md §1.3·§2.1(e)(g)

**맥락** — "여신 초과 수주 승인 게이트"(§7.10, WBS DoD)의 산식은 DESIGN에 문면이 없고(r1 B6), 입금 사실의 정본 테이블이 WBS상 S3-3에 있으나 S3-1 DoD의 "PI 입금 게이트"는 입금 사실 없이 픽스처 조작이 된다. 여신 수치 마스킹은 ADR-0026이 S3-1을 재판정 트리거로 남겼고, 여신한도를 올린 뒤 확정하는 값싼 우회가 게이트 도입과 동시에 생긴다.

**결정** — ① **노출 산식(`credit` 모듈, 계산값이며 저장 열 없음)**: `exposure_after = 미결 SO 합 + 이번 SO 금액 + 미수채권(provider)`, 각 항을 한도 통화(`partners.credit_limit_currency`)로 맞춘다. **미결 SO 술어**(`exposure.open_orders_stmt()` 단일 정의)는 `buyer_partner_id=:p AND confirmed_at IS NOT NULL AND deleted_at IS NULL AND status NOT IN ('COMPLETED','CANCELLED') AND id<>:self`(확정 이력이 있는 ON_HOLD 포함, 접수 단계 ON_HOLD·RECEIVED·COMPLETED 제외 — 음수 집합 형태라 후속 세션이 새 상태를 추가해도 기본 산입)이며 `open_order_amount(so)`가 잔액 식의 유일 정의다(S3-2의 선적분 차감은 S3-3 미수 provider `reflected=True` 등록 릴리스와 같은 PR에서만). **미수채권은 provider 프로토콜**(`ReceivableExposureProvider.outstanding -> ReceivableTerm(reflected, amount|None)`)이며 S3-1 기본 구현은 **`(reflected=False, amount=None)`만 반환하고 0을 반환하지 않는다** — `receivables_reflected=false`·`exposure_is_partial=true`가 결과에 실리고 화면에 **'미수 미반영' 배지를 항상** 표시하며, provider 예외는 통과가 아니라 UNEVALUABLE이다. **선수금 입금분은 노출에서 차감하지 않는다**(과대 방향이라 fail-safe, 입금 오기재·역기록이 여신 과소 산정으로 이어지는 결합을 들이지 않음). 통화는 ADR-0055의 `comparable_amount`를 쓰며 하나라도 `None`이면 `verdict=UNEVALUABLE`이다. **한도 NULL=여신 관리 안 함(`NOT_MANAGED`, 환산·노출 계산을 건너뜀)·0=신용 거래 불가·초과 판정은 strict `exposure_after > limit`·이번 SO 금액이 0이면 `WITHIN_LIMIT`(`NO_INCREMENT`)**이다. UNEVALUABLE은 결과값으로 존재하지만 **확정·승인 요청 경로에서는 승인 우회 없이 거부**된다(ADR-0063). ② **마스킹 재판정(ADR-0026 ② 소진)**: 여신한도·노출은 **마스킹 비대상 유지**다(노출은 판매금액 합이라 원가·마진을 역산할 수 없고 결재자가 판단해야 하는 운영 데이터). 고정 장치는 여신 응답 스키마에 cost·margin·purchase 계열 필드가 구조적으로 없음을 재귀 필드명 스캔으로 검증하는 것이며, **재판정 트리거는 역할 세분화 또는 외부(바이어) 공유 뷰 도입**으로 좁혀 유지한다. 게이트 응답의 CREDIT 결과는 전 역할이 본다(D의 "TRADE·ADMIN만" 제한 삭제, B 문구의 '여신' 마스킹 삭제). ③ **`payments` 입금 원장(S3-3이 그대로 확장하는 정본, 신규 1테이블)**: PkMixin+명시 컬럼(Version·SoftDelete·Actor 없음, INSERT-only, **IMMUTABLE+`revoke_mutations`**), `partner_id`·`pi_id NOT NULL`(S3-3이 채권 입금을 넣을 때 `DROP NOT NULL`+`receivable_id`+"둘 중 정확히 하나" CHECK로 완화)·`kind ∈ {RECEIPT, REVERSAL}`·**부호 있는 `received_amount`**(RECEIPT>0·REVERSAL<0, `payments_kind_sign` CHECK)·`received_currency`·`received_on`(KST 실입금일·미래 불가·소급 허용)·`reference`(필수 텍스트·**유니크 없음** — 부분 정정이 같은 은행 참조로 재입력되는 정상 경로를 막지 않음)·`reverses_payment_id`·`reason`·`recorded_by_id NOT NULL`이며, `UNIQUE(id, pi_id, received_currency)`+**복합 FK**로 역기록은 같은 PI·같은 통화의 원 입금만 가리키고 부분 유니크로 **한 입금은 한 번만 역기록**된다(ADR-05 "반대 부호 신규 기록"). 순입금 정의는 `net_received_for_pi = SUM(received_amount)` 하나다. **입금·역기록은 TRADE+ADMIN, 선수금(`TT_ADVANCE`) 전용**이고 통화 불일치 422(환산 없음)·순입금+금액>`due`(=`split_advance` 선수금) 422 `EXCEEDS_DUE`·EXPIRED·CANCELLED PI 409(`PI_NOT_OPEN`)이며, 기록 후 `converge_payment_status`를 호출한다(ADR-0051). **확정된 SO가 있는 PI의 역기록으로 순입금이 `required` 미만이 되면 응답에 경고+outbox `payments.payment.reversed_after_confirm`을 내되 역기록을 막거나 SO를 자동 취소하지 않는다**(4금). audit `payments.receipt.recorded|reversed`(참조 텍스트 제외)·outbox `payments.payment.recorded|reversed|reversed_after_confirm`(id만). ④ **SO 증적은 3열만**(`credit_verdict ∈ {WITHIN_LIMIT, NOT_MANAGED, APPROVED}`·`credit_approval_id`[FK approvals]·`pi_gate_verdict`) — 확정 배선 마이그레이션(M10)에서 ADD하고 CHECK `(confirmed_at IS NULL)=(credit_verdict IS NULL)`·`=(pi_gate_verdict IS NULL)`·`((credit_verdict='APPROVED') IS TRUE)=(credit_approval_id IS NOT NULL)`, `UNIQUE(credit_approval_id) WHERE NOT NULL`(1승인=1SO), 부분 인덱스 `ix_sales_orders_open_exposure`를 둔다. 열 분류는 SYSTEM이고 트리거는 쓰지 않는다(CHECK는 게이트 통과 기록 없이 `confirmed_at`만 채우는 원시 UPDATE를 막지만 정상 코드의 위조까지는 막지 못한다). 상세 증적은 ADR-0063의 `gate_evaluations`다. ⑤ **승인 요청은 명시 동작**이다: `POST /sales-orders/{id}/approval-requests`(TRADE+ADMIN, `Idempotency-Key`, 본문 `{version}`)가 거래처→SO 잠금→`spec.snapshot(lock=True)`→`request_approval`을 호출하고 excess≤0 422·UNEVALUABLE 422이며 같은 스냅샷 재요청은 기존 행 반환이다. `SO_CREDIT_EXCEEDED` TargetSpec의 `amount=excess_amount`(한도 통화)·`digest=gate_input_digest`이며 spec 등록과 `consume_approval(` 호출은 같은 PR이다. 여신 조회 엔드포인트는 `/gates`가 흡수한다. ⑥ **여신한도 값 변경은 ADMIN 전용**이다. 한도 값이 바뀌는 쓰기 경로는 실측상 `create_partner`(등록 시 초기 한도)와 임포트 `confirm_staging`(`PartnersImportTarget`) 둘뿐이라 이 2곳에서 ADMIN을 요구한다: 등록 요청에 한도가 값으로 실려 있고 행위자가 ADMIN이 아니면 403 `PARTNERS.CREDIT_LIMIT.ADMIN_ONLY`, `ImportTarget.admin_only_fields`(partners=`credit_limit_amount·credit_limit_currency`)를 도입해 확정 행위자가 ADMIN이 아니면서 `CHANGED`가 그 필드를 건드리거나 `NEW`가 non-None으로 싣고 있으면 **배치 전체 거부**(판정은 확정 시점 행위자)하며 "변경"은 값이 실제로 달라지는 모든 전이(NULL→값·값→NULL 포함, 값이 불변인 재전송 제외)다. `audit partners.credit_limit.set|changed`를 남기고 거래처 등록 폼의 여신 입력은 비관리자에게 비활성이다. ⑦ **확정 통로 순서와 거부의 멱등 미기록**은 ADR-0063·0059를 따르고(성공 확정 200만 `complete`), 여신 직렬화의 잠금 규약은 ADR-0059다.

**근거** — 산식은 "가장 좁은 안전한 결정"이다(DESIGN §7.10 보강 필요): 각 항이 fail-visible해야 하며 "못 셈"을 "없음"과 같게 만들지 않는다(미수 항 None). 미차감은 노출 과대 방향이라 초과가 사람 승인으로 흐를 뿐 막히지 않는다. 마스킹은 ADR-0018의 '값에 대한 지식' 논리가 적용되지 않는다(노출에서 마진을 역산할 수 없다)는 점이 근거이고 기존 마스킹 원장 #2의 결정과 일치한다. 입금 사실을 S3-1이 처음부터 S3-3이 쓸 이름·부호·불변 규율로 만들어야 S3-3 재정의(ADR-05 위반)를 막고 A 그룹 "PI 일부입금 SO 게이트" 테스트가 실제 사실에 기대게 된다. 부호 있는 금액은 kind 분기 합산 결함 소지를 없앤다. 한도 변경 통제는 게이트 우회의 가장 값싼 경로를 닫는 것이며 열람 마스킹과 별개 축이다.

**기각한 대안** — 미수 항을 0으로 합산·미수 미반영이면 확정 차단(S3-3 전 확정 영구 정지), 선수금 입금분 차감(입금↔SO 배분이 S3-3 몫), 한도 통화와 다른 통화가 하나라도 있으면 무조건 UNEVALUABLE, 통화 불일치를 승인 요구로 취급, 여신 마스킹(결재 불능), `payments`+`payment_allocations` 2테이블(소비자 없음)·양수 금액+kind로 부호 결정·은행 참조 유니크, 입금 역기록 시 확정 SO 자동 취소, 확정 시도가 승인 요청을 자동 생성(202), SO 5열(`pi_gate_override_reason`·`confirm_gate_snapshot` 포함), 여신 끔 스위치, 한도 조정 요청 워크플로(승인 유형화는 후속 판단).

**되돌리기 비용** — 낮음(산식·provider·상수 단위, 저장 열 없음)~중간~높음. 마스킹 전환은 ADR-0024 방식 스키마 분기(중간). **`payments` 테이블명·부호 규약·불변 등록·`pi_id NOT NULL`은 S3-3이 소비하므로 배포 뒤 변경은 데이터 이관**(그래서 지금 확정). SO 증적 3열+CHECK는 마이그레이션 1건이며 나중 추가는 확정 행 백필이 필요(높음)하므로 S3-1에 넣는다. 입금 권한 축소·`EXCEEDS_DUE` 완화는 서비스 1곳(낮음).

**영향 세션** — S3-1 PR-9(`credit` 모듈)·PR-10(payments)·PR-12(증적 3열·확정 배선) / S3-2(`open_order_amount` 선적분 차감 — 미수 provider 릴리스와 같은 PR) / S3-3(미수 provider 등록·기본 구현 잔존 금지 테스트·`payments` 확장·선수금 미차감 재판정·통화 불일치 입금·잔금·초과분 입금 경로) / S4-1(여신 잠금 방식 P4 ADR) / P7(은행 CSV 이중 입력 탐지) / S5(자동 경로도 `confirm_sales_order`로만).
