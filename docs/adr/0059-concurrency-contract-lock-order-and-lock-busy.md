# ADR-0059: 동시성 계약 — 전역 잠금 순서 LOCK_ORDER·거래처 잠금 3모드·55P03/40P01은 409 LOCK_BUSY·헤더 잠금+version bump·제약명 기반 오류 번역·에러 도메인은 소유 모듈명

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — A 묶음 A13, B 묶음 B8, E 묶음 E3(잠금)·E10, 통합 X-37~X-43)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §17.1~17.4·§18.1·§20 J·H / ADR-0005 / PROGRESS 함정 ②·⑨ / docs/plans/s3-1/design-A.md A13, design-B.md B8, design-E.md E3·E10, design-integrated.md §1.4·§2.4·§2.9

**맥락** — 전표·승인·입금·확정이 처음으로 잠금을 본격 사용한다. A·B·C·E·F가 잠금 순서 문구를 4종으로 각자 적었고(C6은 "SO→거래처", A·B·E는 "거래처→SO"), 잠금 대기 초과 응답 코드가 4중 정의(`COMMON.CONCURRENCY.LOCK_BUSY`·`CONCURRENCY.LOCK.BUSY`·`LOCK_TIMEOUT`…)이고, 앱 역할의 `lock_timeout=5s`(55P03)·교착(40P01)은 현재 핸들러가 없어 500으로 샌다. 에러 도메인 접두도 `TRADE`·`TRADE_DOCS` 등으로 갈렸다.

**결정** — ① **전역 잠금 순서 `LOCK_ORDER`**(상수, `trade_docs/locking.py`, 변경은 ADR): `(0) 멱등 claim 행 → (1) order_intakes → (2) partners(바이어) → (3) QT → (4) PI → (5) SO → (6) PO → (7) approvals → (8) 라인(id 오름차순) → (9) doc_number_seq(항상 마지막)`. **부분수열은 허용**되고(순서만 지키면 건너뛸 수 있다) 위반만 금지이며, 한 트랜잭션은 거래처 행을 최대 1개만 잠근다(벌크는 건별 독립 트랜잭션). 잠금 전에 무잠금 조회로 부모 id를 얻고 잠근 뒤 재확인한다(SO의 거래처는 ORIGIN 불변이라 안전). 경로별: 확정 0→2→3→4→5→7→8→9 / 승인 결정·소비·무효 0→2→5→7 / 입금·역기록 0→3→4(PI 게이트 직렬화) / SO 편집·취소 0→3→4→5→7→8 / 참조 생성 0→(상위 전표)→8→9 / 인테이크 확정 0→1→(거래처 KEY SHARE)→9. C6의 "SO→거래처" 문구는 이 순서로 정정되고 승인 결정은 무잠금으로 SO·거래처 id를 얻어 거래처→SO→approvals 순으로 잠근다. 거래처 잠금은 여신 직렬화가 필요한 경로(SO 확정·승인 요청/결정/소비)에만 걸고 참조 생성·편집·취소·입금·역기록은 자기 사슬만 잠근다(`lock_chain(doc, with_partner=False)`). ② **거래처 행 잠금 모드**: 여신 직렬화 경로=**`FOR NO KEY UPDATE`**(`lock_buyer_for_credit`, `populate_existing`으로 잠금 후 한도를 새로 읽음 — 자식 행 INSERT의 `FOR KEY SHARE`와 비충돌), 유형·활성 검증 소비자(전표 생성·PO·자재·SKU 참조 검증)=**`FOR KEY SHARE`**, 유형 해제(임포트)=`FOR UPDATE`. 여신 체크의 "확인→기록" 직렬화 방식은 §17.2가 P4 ADR로 남긴 것을 **S3-1이 여신 체크에 한해 행 잠금으로 선행**하며 S4-1이 advisory 등으로 바꿀 때는 `lock_buyer_for_credit` 내부만 교체하고 `LockedBuyer` 토큰·순서표·409 계약은 승계한다(ADR-0064). ③ **잠금 대기 초과·교착 = 409 `COMMON.CONCURRENCY.LOCK_BUSY` 1건**: `sqlalchemy.exc.OperationalError` 중 SQLSTATE **55P03·40P01만** 매핑하고(문구 "다른 사용자가 처리 중입니다. 잠시 후 같은 동작을 다시 시도해 주세요. 입력한 내용은 저장되지 않았습니다.") **57014(statement_timeout)는 매핑하지 않고 500 유지**한다(30초 초과 쿼리에 "다른 사용자가 처리 중" 문구는 거짓이고 결함 신호는 fail-visible이어야 한다). 로그에는 sqlstate·경로만 남기며 UoW가 롤백한 뒤 응답하므로 같은 트랜잭션의 멱등 claim도 롤백되어 같은 키 재시도가 안전하다. **구현·소유는 PR-2(플랫폼 기반)**이고 A13·B8·C의 해당 항목은 이를 참조만 하며 B의 `CONCURRENCY.LOCK.BUSY`·C의 `LOCK_TIMEOUT`은 폐기한다. ④ **전표 쓰기 순서**: 모든 쓰기(라인 포함)는 헤더 행 `SELECT FOR UPDATE`→요청 `version` 대조(불일치 409)→변경→헤더 version 증가이며 라인만 바뀌어도 헤더 version이 오른다(`bump_header_version` 1곳 — S1-3 PR-3의 "부모 version 미증가 우회" 결함 재발 방지). 시스템 수렴(스윕·입금·연쇄)도 `VersionMixin` 때문에 version이 오르며 편집 중 사용자의 stale 저장은 409로 걸러진다. **요청 본문의 낙관 잠금 필드명은 `version`**(저장소 관용, `expected_version`은 임포트 내부 필드뿐)이다. ⑤ **멱등**: 생성·참조 생성·개정·동결 전이(확정·발행)·취소 액션은 `Idempotency-Key` 필수(스코프 액터×엔드포인트×키, 재수신=최초 결과, 같은 키 다른 지문은 기존 `COMMON.IDEMPOTENCY.KEY_CONFLICT` 409 — 신규 코드 없음). **확정 API는 200만 성공이며 거부는 전부 4xx 예외로 멱등 결과에 기록하지 않는다**(승인·override 후 같은 키로 재시도하면 새 판정을 받는다). 프런트의 확정 키는 (SO id, version) 조합이 바뀔 때만 새로 만든다. DB UNIQUE(`doc_number`·PI→SO·중복 바이어 PO·복제본·라인)가 마지막 방어선이다. ⑥ **제약 위반 번역은 `map_integrity_error()` 1곳에서 제약명 접두로 분기**한다: 유니크 위반은 사용자 문구(409)로, **CHECK 위반은 "서비스 선검증 누락 버그"로 취급해 ERROR 로그(값은 `log_context`에만)+일반 422/409**로 내며, 미등록 제약 위반은 **500 유지+로그(제약명만, 값 미포함)**(삼키면 fail-open). 응답·`last_error`에 DB 예외 원문을 싣지 않고 IntegrityError 뒤 세션을 재사용하지 않는다(`PendingRollbackError`). ⑦ **에러 코드 도메인 = 소유 모듈명 대문자**로 하고 실재 모듈이 아닌 `TRADE`는 폐기해 `TRADE_DOCS`로 통일한다. 같은 사건은 하나로 통합한다(후속 생존·원천 자격·수량 초과·바이어 PO 중복·동결). **신규 코드는 56종**(TRADE_DOCS 19·COMMON 1[`CONCURRENCY.LOCK_BUSY`]·APPROVALS 12·ORDER_INTAKE 9·GATES 3·TRADE_CHAIN 1·ORDER_BOARD 3·PAYMENTS 5·POLICIES 2·PARTNERS 1)이고 재사용은 `VALIDATION_INVALID_FIELD`·`CATALOG.PRICE.NOT_EFFECTIVE`·`COMMON.CONCURRENCY.VERSION_CONFLICT`·`COMMON.IDEMPOTENCY.KEY_*`·`IMPORTS.*`다. 카탈로그 전수 테스트(3세그먼트·문구 ≥10자+조치 힌트어)는 PR마다 자기 코드를 추가하며 통과하고 금액·계좌·사유 원문은 detail·로그에 넣지 않는다. API 경로 접두는 `/api/v1`을 라우터가 한 곳에서 부착한다.

**근거** — 두 경로가 반대 순서로 같은 두 행을 잡으면 교착이다(승인 결정=SO→거래처와 확정=거래처→SO). 거래처는 SO의 상위(1:N)이고 여신 직렬화는 거래처 단위 조율이므로 coarse→fine 순서가 자연스럽다. `FOR UPDATE`는 자식 행(QT·PI·SO·payments) INSERT의 FK 검사 잠금과 충돌해 무관한 신규 작성까지 막고 `FOR NO KEY UPDATE`는 비충돌이면서 같은 거래처 여신 체크끼리·임포트의 partners `FOR UPDATE`와는 직렬화된다. 잠금 순서 위반을 리뷰가 아니라 헬퍼(`lock_chain`·`lock_lines_for_consumption`)와 아키텍처 테스트로 구조화한다. 프런트 `ApiError`는 서버 `message`를 그대로 보이고 상태별 분기가 없으므로 409 vs 503은 와이어 취향이고 A·B·C 3:1 정합에 따라 409+코드값 구분을 택했다. CHECK 위반을 사용자 오류로 위장하지 않는 것은 선검증 누락을 fail-visible로 남기기 위해서다.

**기각한 대안** — 잠금 대기 초과에 503·`Retry-After` 헤더(소비자 없음), 57014를 함께 매핑(문구가 거짓), advisory lock(정수 키 중앙 레지스트리 없음), 거래처 `FOR UPDATE`/`FOR SHARE`(자식 INSERT 블록 또는 `NO KEY UPDATE`와 충돌해 비블록 증명 붕괴), 모든 경로에서 거래처 잠금(불필요한 직렬화), 승인 결정을 SO→거래처 순으로, 확정 거부를 멱등 결과로 재생(승인 후 재확정이 영원히 옛 거부를 받음), 요청 본문 `expected_version`, 도메인 접두 `TRADE`/`SALES`/`FINANCE` 병존, 미등록 제약 위반을 일반 422로 삼킴.

**되돌리기 비용** — 중간. 잠금 단위를 advisory로 바꾸는 것은 헬퍼 1곳+동시성 테스트 재실행(낮음), 409 계약은 프런트 매핑 동반(낮음~중간)이지만 **잠금 순서표 변경은 전 확정·결정·입금 경로 재검증(높음) — 그래서 지금 고정**한다. 에러 코드명 변경은 프런트 분기 영향이 있어 지금 확정한다.

**영향 세션** — S3-1 PR-2(핸들러·`LOCK_ORDER`·아키텍처 골격)·PR-5~15(전 경로가 순서 준수) / S3-2(선적·소비가 `lock_lines_for_consumption` 규약) / S4-1(P4 ADR이 여신 잠금 방식·순서표 승계 결정) / S4-2(할당 직렬화) / 후속 세션 전부(에러 도메인 규칙·`version` 필드명).

**부기 (S3-1 PR-7a, 2026-09-30 — 구현 중 J 테스트가 교착 결함 2건을 잡아 규칙을 보강)** — ① **FK 검사의 암묵 `FOR KEY SHARE`도 잠금 순서의 일부다**: 자식 행(SO 등)을 INSERT하면 DB가 FK가 가리키는 조상 행(QT·PI·거래처)에 키 공유 잠금을 **암묵으로** 잡는다. 조상 중 일부만 명시적으로 잠그고 INSERT하면 "하위 명시 잠금 → 상위 암묵 잠금" 역순이 생겨 상위를 `FOR UPDATE`로 먼저 잡는 경로(PI 취소: QT→PI)와 교차 교착한다(PI→SO 생성이 PI만 잠갔던 초기 구현에서 실제 재현 — 지금은 `lock_chain`으로 QT→PI를 명시적으로 잠근다). **규칙: 자식 INSERT 전에 FK 경로의 모든 조상 행을 LOCK_ORDER 순서로 명시적으로 잠근다**(테이블 잠금 순서 계측 테스트가 고정). ② `Session.begin_nested()`는 **진입 시 세션을 먼저 flush한다** — 유니크 경합을 번역하려는 변경은 SAVEPOINT **안에서** 대입·flush해야 한다(밖에서 대입하면 진입 flush의 IntegrityError가 세션을 깨뜨려 `PendingRollbackError` 500).

**부기 (S3-1 PR-7a 적대 검토, 자율 확정 2026-09-30 — 바이어 PO 정규화 보강)** — 중복 바이어 PO 차단(§17.4)이 이 계약의 마지막 방어선인 DB 부분 유니크의 **키**에 의존하므로 키 산출을 보강한다: NFKC 뒤 **대시류(U+2010~2015·U+2212·U+FE58 등)를 '-'로 통일**하고 **불가시 문자(Cf·Cc·Mn·Me — 제로폭·변형 선택자·CGJ — 및 Hangul filler U+115F·1160·3164·FFA0)를 제거**한다(사유: Word·Excel 자동 교정의 en-dash, 복붙 오염이 'PO–123'과 'PO-123'을 다른 키로 만들어 중복 차단을 우회). 대시 외 구두점은 계속 보존('PO-1'≠'PO1'). 규칙이 바뀌면 저장된 키는 재계산 마이그레이션이 필요하나 S3-1 시점 행이 없어 비용이 낮다.

**부기 (S3-1 PR-9a, 자율 확정 2026-10-01 — 구현 중 J 테스트가 교착 1건을 잡아 규칙을 보강)** — **같은 트랜잭션이 앞서 멱등 행(`idempotency_keys.actor_user_id` FK)을 INSERT하면 그 행위자 `users` 행에 `FOR KEY SHARE`를 쥔다.** 그 뒤 같은 `users` 행을 `FOR UPDATE`로 잠그는 직렬화 지점(대결 등록의 위임자 잠금)은 동시 요청끼리 서로의 KEY SHARE를 기다리는 교착이 된다(PR-7a ①의 FK 암묵 잠금과 같은 계보 — "자기 앞선 INSERT가 이미 쥔 약한 잠금과 충돌하는 강한 잠금을 요청하지 않는다"). **규칙: 이미 FK 참조로 KEY SHARE가 걸릴 수 있는 행의 단순 직렬화는 `FOR NO KEY UPDATE`로 한다**(여신 거래처 잠금이 `NO KEY UPDATE`인 이유와 같다). 승인 결정·소비·무효 경로의 잠금 순서(거래처→SO→approvals)는 계측 테스트가 실측 SQL 순서로 고정한다(`void_for_target`은 대상 편집·취소 트랜잭션이 이미 대상을 잠근 뒤 부르므로 approvals 잠금만 건다).
