# ADR-0018: 매입가는 원가다 — 조회 역할에게는 행 자체를 보이지 않는다

- **상태**: 채택
- **날짜**: 2026-07-29
- **관련**: DESIGN.md §2 권한·통제(역할 5종)·§18.1(원가·마진 마스킹, 로그 마스킹)·ADR-0008 / WBS.md S1-1 / §20 G

**맥락** — §2는 "조회는 원가·마진을 API 응답 레벨에서 마스킹"을, §18.1은 "화면에서 못 보는 값이 로그에 평문이면 통제가 우회된다"를 요구한다. S1-1의 매입가 이력이 **이 시스템에 원가가 처음 들어오는 지점**이라, 여기서 원가의 정의와 차단 방식을 고정한다.

**결정** — `price_type = PURCHASE` 이력은 **원가**로 취급한다. 조회(VIEWER) 전용 사용자에게는 필드가 아니라 **행 단위로 보이지 않는다** — 목록에서는 결과와 `total` 건수 양쪽에서 제외하고, 단건 조회는 **404**(403이 아니다). 로그 마스킹 프로세서의 민감 키에 단가·금액 계열을 추가한다.

**근거** — §2의 문언이 "차단"이 아니라 **"마스킹"**이다. 403은 "네가 볼 수 없는 원가가 여기 존재한다"는 사실과 건수를 알려 주고, 존재 사실과 건수만으로도 마진 추정의 단서가 된다 — 마스킹의 목적은 값이 아니라 **값에 대한 지식**을 막는 것이다. 필드만 null로 비우는 방식은 화면에서 "0원"으로 읽히고, 목록 건수로 이력의 존재와 변경 횟수가 그대로 새어 나간다.

**기각한 대안** — ① 필드만 null: 0원으로 오독되고 건수가 샌다. ② 403: 존재를 노출한다. ③ DB 뷰로 분리: 역할이 요청 단위로 결정되므로(§18.1 "인가는 API에서 강제") 연결 단위인 뷰로는 표현할 수 없다.

**되돌리기 비용** — 지금은 조회 필터 1곳과 로그 키 목록. 뒤집으면 S3-1 비용·S6-2 원가·landed cost가 이미 같은 규약을 물려받은 뒤라 전 화면의 응답 계약이 함께 움직인다.

**로그 측 부기 (2026-07-29 — §20 G "로그에 원가 문자열 0건")** — 응답 마스킹만으로는 절반이다. 로그로 새는 경로는 **네** 개였다.

1. **구조화 로그의 키**(`purchase_price` 등) → `SENSITIVE_KEYS` 추가.
2. **느린 쿼리 로그의 SQL** → `events.py`가 처음부터 파라미터를 인자로 받지 않는다(S0-1).
3. **예외 문자열·트레이스백의 `[parameters: {...}]`** → SQLAlchemy 엔진에 `hide_parameters=True`. INSERT 실패가 `handle_unexpected`로 가면 매입가도 비밀번호 해시도 트레이스백째 남는데, 임의의 숫자·해시는 키 이름·값 패턴으로 잡을 수 없다. **이 설정은 환경 분기·토글 없이 고정이며 호출자가 덮을 수도 없다** — dev/prod 분화는 §18.1에 없다. 대가는 바인드 값 비노출이고, SQL 문장과 제약 이름은 남으므로 진단은 유지된다.
4. **PostgreSQL이 보내는 `DETAIL: Failing row contains (…)`** → 마스킹 프로세서가 그 구간을 통째로 지운다. ③으로 막히지 않는 별개 경로다 — `hide_parameters`는 *우리가 보낸* 바인드 값만 가리는데, 이건 **서버가 만든 문자열에 행 전체 값**이 들어 있다. 실측: `Failing row contains (1, 1, BOGUS, KRW, 7654321, 2026-01-01, …)`.

   절단 규칙은 실측으로 세 번 고쳤다. **괄호 짝** → 값 안의 괄호에 뚫린다. **줄 끝** → PostgreSQL이 값 안의 개행을 그대로 실어서 개행 뒤가 남는다(실측). **SQLAlchemy 꼬리표 앞까지** → 사용자가 메모에 `"\n[SQL:"`을 적으면 절단이 거기서 멈춘다(실측). 최종형은 두 겹이다: ⓐ 꼬리표는 **마지막** 등장 위치로 찾는다(값은 항상 진짜 꼬리표 앞에 있다) ⓑ 그래도 삭제 구간 안에 꼬리표가 보이면 위조가 섞인 것이므로 **메시지 끝까지** 지운다 — **fail-closed: 문장을 잃더라도 값을 남기지 않는다.** 제약 이름은 앞 줄이라 어느 경우에도 남는다.

**남는 것 둘** — ㉠ 유니크 위반의 `DETAIL: Key (…)=(…)`는 **키 컬럼 값만** 실리고 진단 가치가 커서 지우지 않는다. 대신 **그런 키를 만들지 못하게** 아키텍처 테스트로 막는다: 유니크 제약·유니크 인덱스에 민감 이름(`redaction.is_sensitive_key`) 또는 금액 이름(`money.is_money_column_name`)이 들어가면 실패한다. 두 개념은 각자 한 곳에서만 정의된다 — 합치면 안 되는 이유는 **판가는 가리지 않지만 돈**이고, 실측 유출 두 번의 당사자가 바로 그 `amount`였기 때문이다(이름 기준 민감 목록만 쓰면 ㉠이 막으려던 경우가 판정 밖으로 빠진다). 구조상 불가피한 예외는 사유와 함께 허용 목록에 등록하며, 현재 1건이다: `user_sessions.token_hash`(세션 조회의 키 자체 — ADR-0013, 위반하려면 sha256 충돌이 필요하고 실리는 값도 토큰이 아니라 해시다). 재검토는 그 목록을 고치는 행위로 기계화됐다. ㉡ 원가가 사람이 쓴 자유 텍스트(메모)에 적히면 어떤 규칙으로도 못 막는다 — 부채 #6(감사 채널 분리, ADR-0008)이 담당한다.
