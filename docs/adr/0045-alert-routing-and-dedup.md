# ADR-0045: 알림 생성 단일 통로 — 수신자 결정 이원화·수신자 포함 dedup 키·IN_APP 채널화

- **상태**: 채택 (S2-3 계획 웹 세션 판정 2026-08-12 — 판정 요청 3·4·6·7·8·10·조건 B·E, PR-1 실장)
- **날짜**: 2026-08-12
- **관련**: DESIGN.md §2 ADR-07·§15·§17.4·§18.1·§20 H / ADR-0012(라우팅 구조/동작 분할)·0015(담당 이관)·0043(디스패처) / GC-C1

**맥락** — ADR-0012가 담당자 라우팅의 **동작**을 S2-3으로 미뤄 두었고, 이제 알림을 만드는 주체가 둘 생긴다(기일 스캔·아웃박스 디스패처). 판단은 셋이다: 생성 통로, dedup 키 구성, 수신자 결정 규칙.

**결정** — ① **알림을 만드는 통로는 `notifications.service.notify()` 하나뿐**이다(조건 B). 스캔도 디스패처도 이 함수를 부르고, `Alert` 직접 생성이 app 전역에 0건임을 아키텍처 테스트가 고정한다. ② **dedup_key는 수신자를 포함한다**: 기일 `{종류}:{대상type}:{대상id}:{문턱}:{수신자id}` / 브리핑 `briefing:{수신자id}:{KST 날짜}` / 에스컬레이션 `esc:` 접두. 멱등은 사전 확인이 아니라 부분 유니크에 부딪히는 `ON CONFLICT DO NOTHING`이다(§17.4). ③ **수신자 결정은 이원화**다 — 공통 순서는 규칙의 명시 수신자 → 담당자이고, 둘 다 없을 때 **DEADLINE은 ADMIN 전원 폴백**(본문에 사유 1줄), **EVENT는 미발송**이다. 운영 알림(배치 실패·포이즌)은 ADMIN이 **정본 수신자**인 별도 경로다. **담당자가 있으면 폴백은 발동하지 않는다**(배타 라우팅 — 조건 E). ④ 비활성·삭제 계정은 어느 경로에서도 수신자가 되지 않는다. ⑤ 알림 규칙 CRUD는 **관리자 전용**이다. ⑥ 이번 실장 채널은 **IN_APP 1종**이고, 이는 ADR-07의 채널 열거(텔레그램/슬랙 웹훅/메일/노션) **밖의 신설 판단**이다(문면 근거는 같은 ADR의 "화면 알림센터"). 외부 커넥터는 S6-3이며, 그전까지 notification_channels·webhook_subscriptions는 **0행**이다.

**근거** — `alerts.dedup_key`는 테이블 전역 부분 유니크이고 `recipient_user_id`는 NOT NULL이라, 한 사건을 여러 명에게 보내면 행이 사람 수만큼 필요하다. 키에 수신자가 없으면 두 번째 사람부터 조용히 탈락하는데, 그 실패는 "중복 발송 0"을 통과하면서 알림만 안 가는 모양이라 가장 늦게 발견된다. 기일 축에서 조용한 미발송은 곧 도과이고 도과의 대가는 인증 실효라, 규칙 공백을 침묵이 아니라 관리자 통지로 메운다(fail-visible). 반대로 일반 이벤트에서 폭을 넓히면 ADR-07이 금지한 전사 폭포에 가까워진다.

**기각한 대안** — 스캔이 alerts를 직접 만드는 별도 경로(규약 이원화), 스캔이 dedup을 선확인한 뒤 이벤트 발행(§17.4가 금지하는 "확인 후 INSERT" — 발행~소비 창에서 중복 이벤트가 무한 누적), 수신자 미포함 키(팬아웃 조용한 유실), 전 경로 ADMIN 폴백(전사 폭포에 근접), 규칙 부재 시 전 경로 침묵(기일 도과가 조용해진다), 일반형 WEBHOOK 커넥터 조기 실장(§15 "대외 최초 발송" 경계의 물리적 담보가 무너진다 — URL 통제 구조가 세트로 필요해진다).

**되돌리기 비용** — 중간. dedup 키 규약을 바꾸면 이미 발송된 알림의 재발송 억제가 한 번 풀린다(같은 사건이 새 키로 1회 더 간다). 수신자 규칙 변경은 코드 한 곳(`resolve_recipients`)이지만 §20 H 테스트가 함께 움직인다.
