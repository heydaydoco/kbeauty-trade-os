# ADR-0013: 로그인 세션은 서버측 `user_sessions` 테이블 + HttpOnly 쿠키

- **상태**: 채택
- **날짜**: 2026-07-27
- **관련**: DESIGN.md §2 권한·통제·§3 / §18.1 / §20 K / WBS.md S0-2

**맥락** — §18.1이 "세션 만료"를, §2가 "퇴사·휴가·담당 변경 시 **계정 비활성 절차**"를 요구하는데 §3 테이블 맵에는 세션을 담을 자리가 없었다. 저장 방식을 정하지 않으면 각 화면이 제각기 토큰을 다루게 된다.

**결정** — 세션을 `user_sessions` 테이블(원문 토큰이 아닌 **sha256 해시**만 저장)에 두고, 브라우저에는 `HttpOnly` + `SameSite=Lax` + prod에서 `Secure` 쿠키로 세션 토큰을 내린다. **로그인 성공 시 항상 새 토큰을 발급하고 요청에 실려 온 기존 세션은 폐기**한다(세션 고정 공격 차단). 만료·폐기 세션은 로그인 시 해당 사용자분을 함께 정리하고, 전역 청소는 S0-2의 `scheduled_jobs` 레지스트리에 배치로 등록한다(실행기는 S2-3).

**근거** — §2의 계정 비활성이 실효를 가지려면 서버가 **이미 발급한 세션을 즉시 무효화**할 수 있어야 한다. JWT 등 무상태 토큰은 만료 전까지 회수가 불가능해 "비활성" 버튼이 거짓말이 된다. 해시만 저장하는 이유는 §18.1의 마스킹 원칙과 같다 — DB가 유출돼도 그 값으로 남의 세션을 탈취할 수 없어야 한다. 동일 오리진(nginx 리버스 프록시, ADR-01)이라 쿠키로 충분하고 CORS·토큰 보관 문제가 생기지 않는다.

**기각한 대안** — ① JWT 무상태: 즉시 무효화 불가로 §2와 정면 충돌, 블랙리스트를 붙이면 결국 DB를 보게 되어 이 결정과 같아진다. ② `localStorage` 토큰: XSS 한 번에 토큰이 그대로 새고 HttpOnly의 보호를 스스로 포기한다.

**되돌리기 비용** — 지금은 테이블 1개와 의존성 1개. 뒤집으면 인증 미들웨어·프런트 저장소·로그아웃·계정 비활성·§20 K 케이스가 함께 움직인다.

**부기(2026-07-27) — 로그인 잠금 해제 경로.** §18.1은 "연속 실패 잠금(5회)"만 정하고 해제를 정하지 않았다. **기본값을 ①15분 자동 해제(`LOCKOUT_DURATION`) + ②관리자 즉시 해제(`POST /api/v1/users/{id}/unlock`, audit 기록)** 두 경로로 확정한다. 자동 해제만 두면 출고 마감처럼 시간이 곧 비용인 순간에 담당자가 15분을 통째로 잃고, 관리자 해제만 두면 관리자가 자리에 없을 때 아무도 못 들어온다. 영구 잠금은 채택하지 않는다 — 관리자 본인이 잠기면 시스템 안에 복구 경로가 없어진다(같은 이유로 **마지막 활성 관리자의 ADMIN 회수·계정 비활성은 차단**하고 그 시도를 `identity.admin.last_one_protected`로 남긴다).

**부기(2026-09-30 — S3-1 계획)** — (자율 확정 — 사후 번복 가능. 위 원문 결정은 고치지 않는다.) 이 ADR이 남긴 **만료 세션의 전역 청소는 배치의 일**이라는 약속이 S3-1에서 이행된다: 잡 `session-purge`(daily@04:25 KST)가 `identity.service.purge_expired_sessions_all`로 `user_sessions.expires_at <= now`인 행을 1,000행 청크로 삭제한다(기존 로그인 시 사용자별 청소와 같은 술어 — 유예 기간을 새로 만들지 않는다). 잡이 임포트하는 모델은 `UserSession`뿐이고 4금 비저촉 사유는 "기술 행 TTL 청소"다. 근거: ADR-0058 / design-F.md F18.

**부기(2026-10-04 — S3-1 PR-16 이행 완료)** — 위 2026-09-30 부기의 `session-purge`(daily@04:25 KST)·`identity.service.purge_expired_sessions_all`이 구현됐다. 술어는 로그인 시 사용자별 청소와 같고(같은 만료 분포에서 남는 집합이 같음을 시험으로 고정), 미만료 세션은 폐기 여부와 무관하게 남는다(청소 직후에도 활성 토큰 인증 유지 실측). audit은 남기지 않는다(기술 행 TTL 청소). 청크 삭제는 `app/core/db/purge.py`의 `purge_in_batches`(1,000행·청크마다 독립 트랜잭션·기준 시각 호출 시작 시 고정·`RETURNING`으로 실삭제 수 계수)가 맡는다. **설계보다 좁힌 점(자율 확정 — 더 엄격한 쪽)**: 후보 행을 `FOR UPDATE SKIP LOCKED`로 집어 **지금 다른 트랜잭션이 잠근 행은 기다리지도 지우지도 않는다** — 진행 중인 멱등 claim의 이어받기(`claim()`의 행 잠금)·세션 `last_seen_at` 갱신과 겹쳐도 청소가 요청 경로를 기다리게 하거나(lock_timeout 409 전파) 이어받는 행을 빼앗지 않고, 남은 행은 다음 회차가 지운다. 실행 결과(`{"deleted": n}`)는 잡 반환값이며 `scheduled_jobs`에 결과 열이 없어 저장되지 않는다(실패만 FAILED+관리자 알림 — 기존 실행기 계약). 시험: `tests/integration/test_ttl_purge_jobs.py`(J — 경계 TTL 정확히·진행 중 claim·활성 세션·청크·재실행 0·실패 알림 / H — 동시 청소 4개·전역×로그인 청소 겹침) + 변이 9종 전원 kill.
