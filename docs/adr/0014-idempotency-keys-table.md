# ADR-0014: 쓰기 API 멱등은 `idempotency_keys` 테이블에 최초 결과를 저장해서 재현한다

- **상태**: 채택
- **날짜**: 2026-07-27
- **관련**: DESIGN.md §17.4·§3 / GC-A3 / §20 J / WBS.md S0-2

**맥락** — §17.4는 "확정·생성 요청에 클라이언트 idempotency key(더블클릭·재시도 흡수, **동일 키 재수신 시 최초 결과 반환**)"를 요구하는데, 그 "최초 결과"를 담을 자리가 §3 테이블 맵에 없었다. GC-A3도 2차 요청이 에러가 아니라 최초 결과를 그대로 받을 것을 요구한다.

**결정** — `idempotency_keys` 테이블을 만든다. 유니크 스코프는 **(actor_user_id, endpoint, idempotency_key)** 3요소이고, 요청 본문의 해시(`request_fingerprint`)를 함께 저장해 같은 키로 다른 내용이 오면 409로 거절한다. 응답 상태코드와 본문을 저장해 재수신 시 그대로 재생한다. 보존 TTL은 **24시간**이며, 만료분 청소는 `scheduled_jobs`의 배치로 등록한다(실행기는 S2-3, 그전까지는 키 발급 시 해당 사용자분을 함께 정리).

**근거** — 스코프에 액터를 넣지 않으면 A가 쓴 키를 B가 재사용했을 때 **B가 A의 응답을 받는다**(정보 유출이자 오작동). 엔드포인트를 넣지 않으면 같은 키로 다른 업무를 부른 요청이 엉뚱한 결과를 재생한다. 본문 해시가 없으면 "같은 키로 금액만 바꾼 재전송"이 조용히 최초 결과로 흡수돼 사용자는 성공했다고 믿는다. 동시 2요청은 UNIQUE 충돌 → 선점 행의 잠금 대기로 직렬화되므로, 뒤늦은 요청은 앞 트랜잭션이 커밋된 뒤 저장된 결과를 읽는다(§17.4 "코드에서 확인 후 INSERT는 race로 뚫린다").

**기각한 대안** — ① 키만으로 유니크: 액터 간 응답 유출. ② 전역 캐시(메모리·Redis): 프로세스 재시작·다중 인스턴스에서 사라져 "재시도가 안전하다"는 계약이 조용히 깨지고, 업무 트랜잭션과 원자적으로 묶이지 않는다. ③ 무기한 보존: 테이블이 단조 증가하고 되돌릴 시점이 없다.

**되돌리기 비용** — 지금은 테이블 1개와 서비스 헬퍼 1개. 뒤집으면 확정·생성 API 전건과 프런트의 재시도 규약(`Idempotency-Key` 헤더)이 함께 움직인다.

**부기(2026-09-30 — S3-1 계획)** — (자율 확정 — 사후 번복 가능. 위 원문 결정은 고치지 않는다.) 이 ADR이 예약한 **만료분 청소 배치**가 S3-1에서 이행된다: 잡 `idempotency-purge`(daily@04:20 KST)가 `idempotency.service.purge_expired_all`로 `idempotency_keys.expires_at <= now`인 행을 1,000행 청크로 삭제한다(기존 사용자별 청소와 같은 술어). S3-1이 확정·생성 API를 대량 추가하고 PO 생성 응답(Full 스키마, 원가 포함)이 24시간 저장되므로 보존을 최소화한다 — 원가가 at-rest로 남는 점은 수용 사실로 ADR-0057에 명기했다. 24시간 이후 재시도는 키가 아니라 상태 검사(전이 409)가 이중 확정을 막는다. 근거: ADR-0058·0057 / design-F.md F5·F18.

**부기(2026-10-04 — S3-1 PR-16 이행 완료)** — 위 2026-09-30 부기의 `idempotency-purge`(daily@04:20 KST)·`idempotency.service.purge_expired_all`이 구현됐다. 술어는 `expires_at <= now`(완료 여부 무관 — 24시간이 지난 미완료 claim도 기술 행)이고 경계는 claim이 찍은 `expires_at`에서 1µs 전 보존·정각 삭제로 고정했다. 지워진 키의 재요청은 재생이 아니라 신규 처리다(그 뒤의 이중 확정은 전이 409가 막는다). 청크 삭제는 `app/core/db/purge.py`의 `purge_in_batches`(1,000행·청크마다 독립 트랜잭션·기준 시각 호출 시작 시 고정·`RETURNING`으로 실삭제 수 계수)가 맡는다. **설계보다 좁힌 점(자율 확정 — 더 엄격한 쪽)**: 후보 행을 `FOR UPDATE SKIP LOCKED`로 집어 **지금 다른 트랜잭션이 잠근 행은 기다리지도 지우지도 않는다** — 진행 중인 멱등 claim의 이어받기(`claim()`의 행 잠금)·세션 `last_seen_at` 갱신과 겹쳐도 청소가 요청 경로를 기다리게 하거나(lock_timeout 409 전파) 이어받는 행을 빼앗지 않고, 남은 행은 다음 회차가 지운다. 실행 결과(`{"deleted": n}`)는 잡 반환값이며 `scheduled_jobs`에 결과 열이 없어 저장되지 않는다(실패만 FAILED+관리자 알림 — 기존 실행기 계약). 시험: `tests/integration/test_ttl_purge_jobs.py`(J — 경계 TTL 정확히·진행 중 claim·활성 세션·청크·재실행 0·실패 알림 / H — 동시 청소 4개·전역×로그인 청소 겹침) + 변이 9종 전원 kill.
