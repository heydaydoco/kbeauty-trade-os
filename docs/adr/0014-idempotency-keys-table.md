# ADR-0014: 쓰기 API 멱등은 `idempotency_keys` 테이블에 최초 결과를 저장해서 재현한다

- **상태**: 채택
- **날짜**: 2026-07-27
- **관련**: DESIGN.md §17.4·§3 / GC-A3 / §20 J / WBS.md S0-2

**맥락** — §17.4는 "확정·생성 요청에 클라이언트 idempotency key(더블클릭·재시도 흡수, **동일 키 재수신 시 최초 결과 반환**)"를 요구하는데, 그 "최초 결과"를 담을 자리가 §3 테이블 맵에 없었다. GC-A3도 2차 요청이 에러가 아니라 최초 결과를 그대로 받을 것을 요구한다.

**결정** — `idempotency_keys` 테이블을 만든다. 유니크 스코프는 **(actor_user_id, endpoint, idempotency_key)** 3요소이고, 요청 본문의 해시(`request_fingerprint`)를 함께 저장해 같은 키로 다른 내용이 오면 409로 거절한다. 응답 상태코드와 본문을 저장해 재수신 시 그대로 재생한다. 보존 TTL은 **24시간**이며, 만료분 청소는 `scheduled_jobs`의 배치로 등록한다(실행기는 S2-3, 그전까지는 키 발급 시 해당 사용자분을 함께 정리).

**근거** — 스코프에 액터를 넣지 않으면 A가 쓴 키를 B가 재사용했을 때 **B가 A의 응답을 받는다**(정보 유출이자 오작동). 엔드포인트를 넣지 않으면 같은 키로 다른 업무를 부른 요청이 엉뚱한 결과를 재생한다. 본문 해시가 없으면 "같은 키로 금액만 바꾼 재전송"이 조용히 최초 결과로 흡수돼 사용자는 성공했다고 믿는다. 동시 2요청은 UNIQUE 충돌 → 선점 행의 잠금 대기로 직렬화되므로, 뒤늦은 요청은 앞 트랜잭션이 커밋된 뒤 저장된 결과를 읽는다(§17.4 "코드에서 확인 후 INSERT는 race로 뚫린다").

**기각한 대안** — ① 키만으로 유니크: 액터 간 응답 유출. ② 전역 캐시(메모리·Redis): 프로세스 재시작·다중 인스턴스에서 사라져 "재시도가 안전하다"는 계약이 조용히 깨지고, 업무 트랜잭션과 원자적으로 묶이지 않는다. ③ 무기한 보존: 테이블이 단조 증가하고 되돌릴 시점이 없다.

**되돌리기 비용** — 지금은 테이블 1개와 서비스 헬퍼 1개. 뒤집으면 확정·생성 API 전건과 프런트의 재시도 규약(`Idempotency-Key` 헤더)이 함께 움직인다.
