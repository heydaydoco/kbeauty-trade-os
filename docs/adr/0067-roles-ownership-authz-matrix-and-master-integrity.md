# ADR-0067: 역할·소유권·권한 매트릭스·마스터 정합 — PO 주체는 TRADE·전표는 회사 공유 자산·AUTHZ_MATRIX가 기계 정본·유형 해제 갭 종결·DocKind 단일 어휘·forbid 래칫

- **상태**: 자율 확정(2026-09-30) — 사후 번복 가능 (S3-1 계획 통합 검토서 §4.2 — F 묶음 F2·F3(ADR-F2·F3), 통합 X-14~X-16·X-44·X-47)
- **날짜**: 2026-09-30
- **관련**: DESIGN.md §2(역할 5종·판정 부기)·§7.7·§12.2·§18.1·§20 K / ADR-0012·0015·0024·0026·0041 / docs/plans/s3-1/design-F.md F8~F13·F15·F17, design-integrated.md §1.1·§1.4·§2.7

**맥락** — S3-1은 전표·승인·인테이크·게이트·보드 등 엔드포인트가 대량 추가되는 세션인데 §2는 PO 주체를 정하지 않았고, §18.1·§20 K의 "소유권"·"타 사용자 전표 URL 403"은 정의가 없다. 마스터 쪽에는 거래처 유형 해제가 참조를 확인하지 않는 갭(PROGRESS 트리거 S3-1)·품번 매핑 삭제 경로 부재·전표 참조 폴리모픽 어휘의 이중(`DOC_PREFIXES`의 약칭 vs C·D가 저장하는 `SALES_ORDER`)·쓰기 스키마 `extra=forbid` 전역 스캔의 트리거가 도달해 있다.

**결정** — ① **역할 매트릭스**: ROLE_SEED·역할 5종은 불변이고 **PO 주체=TRADE**(발주·소싱은 무역 실무, LOGISTICS는 입고·검수, CERT는 인증 — DESIGN §2에 판정 부기). QT·PI·SO 생성·편집·발행/확정·전이·취소는 TRADE·ADMIN(LOGISTICS·CERT·VIEWER 403), 조회는 전 역할이며 **PO 조회는 ADMIN·TRADE·LOGISTICS·CERT=Full, VIEWER=CostHidden 200**(ADR-0057)이다. 인테이크 등록·수정·거부·확정·resolve·담당 변경과 벌크·품번 매핑 등록/삭제는 TRADE·ADMIN, 인테이크·게이트·보드 조회·CSV는 전 역할, 게이트 정책 PUT은 ADMIN(ADR-0065), 승인·대결은 ADR-0061 그대로(서비스 판정=`SERVICE_GATED`), 결재선 조회는 비조회 4역할·편집은 ADMIN이다. ADMIN은 라우터 `require_roles`에서 자동 통과하되 **업무 게이트(승인·게이트)는 통과가 아니다**. 통합 검토가 추가한 행(`bank-accounts` 조회 ADMIN·TRADE/쓰기 ADMIN, 참조 생성·`preview`·`revisions`=TRADE·ADMIN, `status-log`·`export.csv` 전 역할[PO CSV는 VIEWER 원가 열 없음], `payments` 기록·역기록 TRADE·ADMIN/조회 전 역할, `policies` ADMIN, `approval-requests` TRADE·ADMIN, `gates` 조회 전 역할, `gate-overrides` SERVICE_GATED[가격·MOQ=TRADE·ADMIN, 준비도·PI=ADMIN], `users/lookup` TRADE·ADMIN, 품번 매핑 DELETE TRADE·ADMIN)를 포함해 **기계 정본 `AUTHZ_MATRIX`(`tests/architecture/authz_matrix.py`)+프로브 테스트**로 고정한다(완비성: S3-1 신규 모듈 경로 전건이 표에 있어야 하고 stale 행 없음, 프로브: 금지 역할은 정확히 403·허용 역할은 401·403이 아님). ② **소유권 정의**: (a) 역할 스코프(표 밖=403) (b) 부모-자식 소속(자식 id가 부모 소속이 아니면 **404**, 공통 헬퍼 `get_child_or_404`) (c) 당사자성(승인·위임 상세는 비당사자 403 — 존재가 팀 공개 정보, 저장 필터·본인 설정은 타인 id 404 — 존재 오라클 방지). **전표(QT·PI·SO·PO)는 회사 공유 자산**이며 `assignee_id`는 라우팅·알림·이관 단위이지 접근 제어가 아니다(B8·D6 벌크 ASSIGN·§7.4 보드 전체 열람과 양립하는 유일한 해석). **§20 K "타 사용자 전표 URL 403"은 "역할 밖 사용자의 전표 URL 접근 403"으로 해석**한다(DESIGN §18.1·§20 K 해석 보강). 모든 전표 쓰기 서비스는 첫 줄에서 `trade_docs.authz.assert_may_write(actor, doc)`를 호출하는 **seam**을 두어(현재 구현=쓰기 역할 재검증) 소유권을 담당자 한정으로 좁히려면 이 함수 1개만 바꾸면 된다. **확인 순서는 401→403→404→409→422로 고정**(역할 검사가 존재 검사보다 앞 — 존재 오라클 방지)이다. **담당자 유효성**: `assignee_id`는 활성 사용자이고 TRADE 또는 ADMIN 역할 보유(4전표 생성·인테이크 등록·벌크 ASSIGN·FREE 메타 변경), 기본=생성 actor다(기존 handover 일괄 이관 도구는 역할을 검증하지 않는 기존 동작 유지 — 관찰 등재). 응답에는 `assignee_name` 등 **표시명 문자열만** 서버 조인한다. ③ **사용자 디렉터리**: `GET /users/lookup?q=&page&size`(`list_user_lookup`, 응답 `{id, display_name}` 두 키뿐·활성·비삭제·역할 ADMIN·TRADE·기본 `assignee_target=true`)와 C의 `delegation-candidates`가 **`identity.service.list_active_user_names` 하나와 `UserLookupItem` 하나를 공유**하고 기존 `/users`(관리)는 ADMIN 전용이다. ④ **사용자 FK 분류 테스트 `test_user_fk_classification`**: `users.id`를 가리키는 모든 FK 컬럼(ActorMixin의 `created_by_id`·`updated_by_id`는 이름으로 AUDIT 자동 분류)을 `USER_FK_CLASSIFICATION`(ASSIGNMENT·HISTORY·AUTH·PERSONAL·DELEGATION, 사유 포함)에 강제하고 ASSIGNMENT는 `ASSIGNMENT_TARGETS`와 교차 단언하며(기존 비-믹스인 users FK는 PR-2에서 1회 소급 분류) C의 개별 면제 테스트는 이것으로 흡수한다. 신규 4전표 헤더 `assignee_id`는 `ASSIGNMENT_TARGETS`에 label=테이블명으로 등록(D의 `order_intakes`까지 5행)하고 `ASSIGNMENT_COLUMN_NAMES`(이름 4종)는 확장하지 않는다(이력 컬럼 이관 오탐 방지). ⑤ **거래처 유형 해제 갭 종결**: 마스터 축에서는 `find_type_release_blockers`(SUPPLIER 해제→`materials.default_supplier_partner_id`가 이 거래처인 활성 자재 수, OEM 해제→`skus.manufacturer_partner_id`가 이 거래처인 활성 SKU 수)를 `PartnersImportTarget.verify_references`(훅 시그니처에 `target_id` 추가)에서 호출해 임포트 확정 **전체 409**(기존 `IMPORTS.CONFIRM.VERSION_CONFLICT` 문제 행, 신규 에러코드 없음)로 막고, 전표 축은 **확정성 진입(QT 발행·PI 생성·SO 확정·PO 생성·인테이크 확정) 시점에 상대방 유형을 재검증**한다(fail-closed·평가 불능도 통과 아님, 이미 발행·종결된 전표는 무효화하지 않음). **전표 참조 409(활성 전표가 있으면 유형 해제 금지)는 기각**한다(종결·역사 전표가 유형 정리를 영구 봉쇄). 잠금은 ADR-0059(유형 해제=`FOR UPDATE`, 유형 소비=`FOR KEY SHARE`)이고 유형 편집 경로는 왕복 임포트 단일이며 `PartnerTypeLink.deleted_at` 대입 지점을 허용 목록으로 고정하고 A의 `partner_has_open_documents`는 **삭제**한다(죽은 코드). §7.7("차단 지점은 등록이 아니라 게이트")과의 정합: 그 사상은 미완성 값의 등록을 막지 말라는 것이지 이미 성립한 의존(자재의 기본공급사·SKU의 제조사)을 조용히 깨는 변경까지 허용하는 것이 아니다. ⑥ **품번 매핑 삭제**: `DELETE /partners/{partner_id}/item-codes/{item_code_id}`(204, TRADE·ADMIN, 저장소 DELETE 관용대로 본문·version 없음, soft delete·audit·outbox, 타 거래처 id 404)를 신설하고 수정 API는 만들지 않는다(정정=삭제 후 재등록). 기확정 전표는 라인 스냅샷이라 무영향이다. ⑦ **폴리모픽 전표 코드 단일 출처 `DocKind`**(`trade_docs/constants.py`): `QUOTATION·PROFORMA_INVOICE·SALES_ORDER·PURCHASE_ORDER`(풀네임 4값)가 **DB에 저장되는 폴리모픽 전표 참조값의 유일한 어휘**(approvals.`target_type`·gate `subject_type`·후속 expenses·documents `owner_type`)이고 `DOC_PREFIXES: dict[DocKind, str]`(QT/PI/SO/PO)·`DOC_TABLES`는 채번·표시 전용이다(B의 `DocType`·약칭 키는 `DocKind`로 통일). `tasks`·`alerts`·`audit_log`의 `entity_type`은 기존 관용(테이블명)을 유지한다. **`documents`는 S3-1에서 변경하지 않으며**(D가 원본 파일 미보관, QT/PI/SO/PO 첨부 소비자 없음) 후속 소비 세션이 `owner_type`을 확장할 때 `String(13)`의 확폭(값 길이: `PURCHASE_ORDER` 14·`PROFORMA_INVOICE` 16)을 같은 CHECK 재정의 마이그레이션에서 해야 한다는 경고를 부채로 등재한다. ⑧ **쓰기 스키마 `extra=forbid` 전역 래칫**: `tests/architecture/test_write_schemas_forbid.py`가 `app/modules/*/schemas.py`의 `Request/Create/Update/Patch/Payload/Body/Input` 접미 모델을 스캔하고, 기존 미설정 32개는 `LEGACY_FORBID_EXEMPT`에 동결(단조 감소 강제 — 이미 forbid인데 목록에 남거나 삭제·개명된 항목은 실패)하며 **신규 스키마는 전건 forbid**다. 소급은 "그 스키마를 수정하는 세션이 forbid로 전환하고 목록에서 지운다"이며 **S3-1이 수정하는 `PartnerCreateRequest`·`SkuCreateRequest`(및 partners/skus 관련 등록·수정 요청)는 PR-3에서 전환**하고 프런트 회귀를 실측한다(B·C·D의 모듈별 forbid 스캔은 이 전역 스캔에 흡수). ⑨ **목록 CSV는 QT·PI·SO·PO 4종을 포함**(목록과 동일 필터·권한, `EXPORT_MAX_ROWS=50,000` 초과 422, `render_csv` 통로, PO는 헤더 상수 2종[원가 열 포함=ADMIN·TRADE·LOGISTICS·CERT / 미포함=VIEWER])하고 승인함·대결·결재선·인테이크 스테이징 목록 CSV는 미포함(운영 큐·설정이지 "대장"이 아님 — 부채 등재)이다. ⑩ 소급 입력 runbook 양식(`manual-record-form.md`·`incident-sop.md`)의 전표 계열 대응표(QT·PI·SO·PO 4행)와 전표 소급 순서(QT→PI→SO, PO 독립)를 S3-1이 갱신한다(§21 부기 의무).

**근거** — PO를 TRADE에 두는 것은 ROLE_SEED("견적·수주·선적·채권")에 문면이 없어 가장 좁은 안전한 판정이고 `COST_VISIBLE_ROLES`와 단일 출처를 유지한다. 소유권을 담당자 한정으로 좁히면 이관 도구·벌크 ASSIGN·FREE 편집과 모순한다. 번복 여지를 싸게 만드는 seam이 그 함수 1개다. 사용자 FK 전수 분류는 이름 4종 밖 컬럼의 조용한 누락을 막는다(이력 컬럼을 이관 스캔에 넣으면 이관이 과거 결정 기록을 바꾸는 오탐이 생긴다 — ADR-0015). `DocKind`를 풀네임으로 정한 것은 approvals·documents·certifications의 저장소 관용(대문자 풀네임)과 C·D의 기존 저장값 `SALES_ORDER`가 이미 그렇기 때문이다. 래칫은 소급이 공개 API 계약 변경(여분 필드 조용한 무시→422)이라 프런트 회귀 실측이 필요해 S3-1 범위 밖으로 두면서도 신규 스키마의 증가를 막는다. 거래처 유형 해제 판정은 마스터 축에서 §12.2 ③(원자적 확정)과 자연스럽게 결합하고 전표 축은 게이트가 fail-closed로 잡는다.

**기각한 대안** — PO 주체를 LOGISTICS·신규 역할·CERT 403으로, 작성자·담당자 한정 쓰기(`NOT_ASSIGNEE` 403), 인테이크 조회를 LOGISTICS·CERT·VIEWER에 403, `ASSIGNMENT_COLUMN_NAMES` 이름 확장, 역할 검사보다 존재 검사를 앞에, 유형 해제 시 전표 참조 409, 유형 해제 수정 화면·PATCH 신설(확정 우회 경로 증가), 약칭 `DOC_PREFIXES`를 DB 폴리모픽 코드로 저장, `tasks.entity_type` CHECK 추가, `documents.owner_type` 선확장, forbid 기저 클래스 도입·기존 32개 즉시 소급, 승인·인테이크·결재선 목록 CSV, `partner_has_open_documents`.

**되돌리기 비용** — 낮음~중간. 매트릭스는 상수+테스트 파라미터라 완화(403→200)는 무해하고 강화는 프런트 영향이며 PO 주체를 신규 역할로 옮기는 것은 역할 마이그레이션(중간). 소유권을 담당자 한정으로 좁히는 것은 `assert_may_write` 1함수+에러코드+프런트 문구지만 이관·벌크·FREE와 동반 재설계(중간). 유형 해제 차단 조정은 서비스 함수 1개(낮음), `DocKind`는 상수 파일 1개(값 변경 시 소비자 테스트가 잡음), 래칫은 테스트+상수(낮음)이다.

**영향 세션** — S3-1 PR-2(테스트 프레임워크 골격·기존 users FK 소급 분류)·PR-3(유형 해제·품번 삭제·forbid 전환)·전 PR(매트릭스 행 추가) / S3-2(선적·자기 확정 시점에 `require_partner_of_any_type(lock=True)` 호출·`DocKind` 사용) / S3-3(documents 전표 첨부·확폭·QT/PI 파일 첨부 소비) / S3-4(expenses 참조 전표 코드) / S6-1(AI 원본 보관 `ORDER_INTAKE` owner_type) / 후속 모듈 수정 세션(forbid 소급).

**부기(2026-10-03 — S3-1 PR-15a, ③ 담당자 디렉터리 기본값·② 담당자 역할 규칙의 적용 범위)** — (자율 확정 — 사후 번복 가능. 위 원문 결정은 고치지 않는다.) ① **`GET /users/lookup`의 `assignee_target` 기본값은 false(종전 동작 — 활성 전원)로 둔다.** 원문 ③은 '기본 `assignee_target=true`'지만, 이 엔드포인트는 PR-15a 이전부터 QT·PI·SO·PO 화면의 담당자 후보 목록으로 쓰이고 있어 기본값을 true로 바꾸면 기존 화면의 후보가 조용히 줄어든다(호출부 무수정 회귀). 그래서 PR-15a는 `q`·`assignee_target`을 **읽기 전용 추가**만 하고, 신규 화면(보드 담당자 필터·벌크 ASSIGN 콤보박스 — PR-15b)이 `assignee_target=true`를 명시한다. 원문과의 차이는 "기본값을 누가 정하느냐"뿐이고 서버측 강제(벌크 ASSIGN의 활성+무역/관리자 검증)는 기본값과 무관하다. ② **담당자 역할 규칙(활성+TRADE/ADMIN 보유)은 현재 벌크 ASSIGN에서만 강제된다** — 사전 422 + 건별 트랜잭션 안 재확인(TOCTOU). 원문 ②가 열거한 나머지 경로(4전표 생성·인테이크 등록·FREE 메타 변경 단일 통로)는 아직 **활성만** 본다 — **부채**(소급은 각 모듈 수정 세션 또는 전용 소수정; 8a 기록과 같은 항목. 소급 시 `identity.ASSIGNEE_TARGET_ROLES` 단일 출처를 쓴다 — 벌크도 그 상수를 쓴다). 벌크만 엄격한 동안에는 "단일 통로로는 지정되는 담당자가 벌크로는 422"인 불일치가 있다(더 엄격한 쪽이라 안전 방향). **되돌리기 비용**: 낮음 — ① 기본값은 쿼리 모델 기본값 1줄(true로 바꾸면 기존 화면 호출부에 `assignee_target=false` 명시 또는 회귀 수용), ② 소급은 경로마다 검증 함수 1줄+시험.

**부기(2026-10-04 — S3-2 계획)** — (자율 확정 — 사후 번복 가능. 위 원문 결정은 고치지 않는다.) **LOGISTICS 행**: `AUTHZ_MATRIX`에 **물류(LOGISTICS)의 첫 전표 쓰기 행**을 더한다 — 선적 헤더(FREE·국가)·출고지시·당사자·통관 기록·선적 마일스톤 계획/실적/초안·통보 = A·T·L, 선적 생성·라인·취소 = A·T, OEM 마일스톤 = A·T, 휴일 쓰기·마일스톤 세트 쓰기 = A 전용. 통제 접두어에 `/api/v1/shipments`·`/api/v1/holidays`·`/api/v1/item-profiles/{profile_id}/milestone-types`를 등재한다. 전표 = 회사 공유 자산·`DocKind` 단일 어휘·forbid 래칫 원칙은 그대로다(선적 쓰기 스키마 전부 `extra="forbid"`). 근거: ADR-0079 / design-integrated.md §2.9.
