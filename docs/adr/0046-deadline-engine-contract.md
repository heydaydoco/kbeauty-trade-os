# ADR-0046: 기일 엔진 1차 계약 — 문턱 데이터화·"지났다" 의미론·스캔 직접 호출·만료일 포함 키·D-3 에스컬레이션·브리핑·링크 문서 삭제 409

- **상태**: 채택 (S2-3 계획 웹 세션 판정 2026-08-12 — 안건 ②·③(브리핑)·⑦, 판정 요청 3·6·8·9·19, PR-2 실장 2026-09-20. §0-3 ②의 키 세그먼트 해석은 사후 승인 대상)
- **날짜**: 2026-09-20
- **관련**: DESIGN.md §4.7·§5.2·§2 ADR-07·§15·§17.4·§17.6·§20 C·H·J / ADR-0039(스윕)·0044(실행기)·0045(알림 코어·dedup) / GC-C1 / PROGRESS 관찰 "[S1-3] 문서 유효기간 기일 스캔 부재"·"문서 soft delete × 태스크 링크"

**맥락** — S2-2가 만료일·리드타임의 순수 함수로 상태를 수렴시켰고(ADR-0039), PR-1이 알림 생성 코어와 실행기를 세웠다(ADR-0044·0045). 남은 것은 "언제, 누구에게, 몇 번" — 기일 알림의 판단 규칙이다. 판단은 여섯이다: 문턱의 출처, 문턱 통과의 의미, 스캔→알림 경로, dedup 키의 세그먼트, 에스컬레이션 발동 조건, 문서 삭제와의 상호작용.

**결정** — ① **문턱은 데이터다**(ADR-11): `alert_rules.config.thresholds`(양의 정수 목록)가 정본이고 부재·비정형이면 기본 D-180/90/30(GC-C1 예시 문면). 규칙 event_type은 `certifications.expiry.approaching` / `documents.validity.approaching`. ② **문턱 통과 = "지났다"**: 오늘 D-88이면 D-90분은 발송된 상태여야 하고(결번 스캔 뒤 지각 발송 포함) D-30분은 아직이다(GC-C1). ③ **스캔은 코어 `notify()`를 직접 부르고 아웃박스를 경유하지 않는다**(판정 요청 3 (가)) — 멱등 장치는 코어의 `ON CONFLICT DO NOTHING` 하나뿐이고, 사전 확인은 두지 않는다(§17.4). ④ **dedup 키 = `deadline:{대상type}:{대상id}:{문턱}@{만료일}:{수신자id}`**(도과 `overdue@{만료일}`, 에스컬레이션 `esc:…:D-3@{만료일}`) — ADR-0045의 5세그먼트 골격 그대로이며 **문턱 세그먼트가 만료일을 품는다**. ⑤ **후보 = 활성·만료일 있음·종결 2태(반려·중단) 제외 인증 전건(RENEWING 포함=갱신중 도과, EXPIRED 포함=도과 — 상태 전이 없음) + 활성·`valid_until` 있는 문서 전건**. 문서는 담당자 컬럼이 없어 규칙 → ADMIN 폴백 경로만 탄다. ⑥ **D-3 에스컬레이션 = D-3 이내(도과 포함)이고 그 건의 기일 알림 중 미확인이 남아 있을 때, ADMIN 전원(판정 요청 8)에게 각 1건** — 판정은 이번 스캔이 새로 만드는 알림보다 앞이다. ⑦ **데일리 브리핑은 담당 건 보유 활성 사용자만 각자 1통**(판정 요청 9), 키 `briefing:{KST날짜}:{수신자id}`(ADR-0045 ②의 표기를 코어 구조에 맞춰 정정 — 부기 참조), 09:00 KST 고정. ⑧ **태스크가 서류로 연결 중인 문서의 soft delete = 409 `DOCUMENTS.DOCUMENT.LINKED_TO_TASK`**, 선해제 후 삭제(판정 요청 19 (나)). 활성 링크만 센다. ⑨ 실행 수단 = 실행기 잡 `deadline-scan`(daily@06:30 — 스윕 06:00 뒤)·`daily-briefing`(daily@09:00) + CLI 수동 겸용(ADR-0039 계보). 건별 독립 트랜잭션(§17.6). ⑩ 도과는 저장하지 않는다 — `is_overdue`·`overdue_days`는 뷰 계산값이다(안건 ⑦).

**근거** — 만료일이 키에 없으면 **같은 인증 행이 갱신 주기를 거쳐 새 만료일을 얻을 때**(만료 포함 유니크 — 만료 후 재개=기존 행 경유) 두 번째 주기의 D-180이 첫 주기의 행에 막혀 영원히 나가지 않는다. 그 실패는 "중복 발송 0"을 통과하면서 알림만 안 가는 모양이라 가장 늦게 발견되고, 대가는 인증 실효다. GC-C1 문면 "동일 **만료 건**"도 만료일이 다르면 다른 건으로 읽는 것이 자연스럽다. 정각 발송은 하루 결번(worker 다운·미스파이어 수렴 1회)에 문턱을 통째로 잃는다 — "지났다" 의미론은 결번을 자동 복구한다. 에스컬레이션을 이번 스캔 생성분보다 앞서 판정하는 이유: 오늘 처음 D-30을 받은 담당자에게 같은 순간 관리자 에스컬레이션까지 붙이면 "안 읽었다"가 아니라 "받을 틈이 없었다"인데도 발동한다. 링크 문서 삭제 409의 이유: 스캔이 활성 문서만 도는 순간, 링크된 채 삭제되는 문서는 유효기간 알림을 조용히 잃는다(무역 역할이 문서 삭제로 인증 증빙 상태를 간접 변경하는 교차 지점).

**기각한 대안** — 스캔이 이벤트를 발행하고 디스패처가 알림화(발행→소비 창의 중복 이벤트 누적 — §17.4 위반), 만료일 없는 키(갱신 주기 조용한 도과), 정각 발송(결번 손실), 에스컬레이션을 같은 스캔의 생성분까지 보고 판정(받을 틈 없는 발동), 브리핑용 코어 시그니처 확장(단일 통로 취지 약화 + 담당 이관의 "꼬리=수신자" 전제 파손), 문서 삭제 시 태스크 링크 자동 해제(태스크 편집 권한 없는 역할의 간접 변경 — 판정 (가) 기각분), tasks.due_date 스캔(WBS 문면 밖 — 관찰 등재).

**되돌리기 비용** — 낮다. 잡 2행을 끄면(is_enabled) 알림이 멈추고, 이미 만들어진 alerts는 남는다. 키 규약을 바꾸면 같은 건이 새 키로 1회 더 간다(ADR-0045와 같은 성격). 409 가드는 서비스 한 곳이다.

**부기(2026-09-20 — 실기동 관통·자기 적대 검증 반영, 5건)**: ① 에스컬레이션 판정은 **현재 만료일 스탬프**의 기일 알림만 센다 — 관통에서 만료일 정정 직후 옛 주기의 미확인 D-30이 새 주기 에스컬레이션을 즉시 발동시킨 것을 잡았다. ② **도과 건에는 지난 문턱을 소급 발송하지 않는다**(도과 알림 1건이 전부 — 반입 첫 스캔 소음 방지, 계획서 §0-3 ⑨). ③ 건별 집계는 **커밋 뒤에만** 합산한다(같은 건의 뒤 INSERT 실패로 롤백되면 앞서 센 알림이 거짓이 된다). ④ 건별 격리 배치의 실패 건이 1건이라도 있으면 **잡을 FAILED로 올린다**(§15 실패 알림 — 특정 건이 매일 실패해도 잡 OK·알림 0인 "조용한 도과" 차단). ⑤ 알림 제목은 컬럼 길이(200)로 절단(템플릿명 200자+접두 → 그 건만 영구 미발송이던 구조 결함). 브리핑은 수신자별 실패 격리 + 같은 트랜잭션 활성 재확인(목록 후 비활성화 시 ADMIN 폴백이 관리자 본인 슬롯을 점유하던 창 폐쇄) + 과거 브리핑은 "미확인 알림" 수에서 제외. 자기 적대 검증 전문은 PROGRESS "현재" 절 PR-2 항목.
