# ADR-0017: 단가 이력은 종료일 없는 발효일 이력으로 쌓고, "단가 없음"은 오류로 실패한다

- **상태**: 채택
- **날짜**: 2026-07-29
- **관련**: DESIGN.md §4.1("그때 단가" 분쟁 대비)·§17.4·§2 ADR-02 / WBS.md S1-1·S3-1 / §20 A

**맥락** — §4.1은 "판가·매입가는 이력 테이블로 변경 추적 — 전표의 단가 스냅샷과 이중 안전"을 요구한다. 이력의 표현 방식(기간형 vs 발효일형)과 "그 시점에 단가가 없을 때"의 거동을 먼저 고정하지 않으면, S3-1의 전표 단가 스냅샷이 각자 다른 기본값을 들고 붙는다.

**결정** — `sku_prices(sku_id, price_type[SALES|PURCHASE], currency, effective_from(date), amount(정수 최소단위))`로 두고 **종료일은 저장하지 않는다**(다음 행의 발효일이 곧 이전 행의 종료다). 멱등 키는 부분 유니크 `(sku_id, price_type, currency, effective_from) WHERE deleted_at IS NULL`(§17.4). 기준일 조회는 `effective_from <= 기준일` 중 **최댓값 1행**을 돌려주며, 해당 행이 없으면(최초 발효일 이전 등) **명시적 오류로 실패한다 — 0이나 null을 돌려주지 않는다.**

**근거** — 종료일을 저장하면 기간 겹침이 표현 가능해지고, 겹친 이력은 "그때 단가"를 두 개로 만든다(§4.1의 목적 자체가 무너진다). 종료일이 없으면 겹침이 **원천적으로 불가능**하다. "단가 없음"을 0으로 돌려주면 금액 0원 전표가 조용히 생기고(§20 A "확정 건 단가 불변"이 잡을 수 없는 지점이다 — 애초에 틀린 값이 확정되기 때문), null을 돌려주면 호출자마다 다른 기본값이 붙는다. 발효일을 `date`로 두는 것은 §2 ADR-02의 UTC 규율이 시각(timestamptz)에 대한 것이고 단가 발효는 업무 날짜이기 때문이다.

**기각한 대안** — ① `valid_from`/`valid_to` + `EXCLUDE` 제약: `btree_gist` 확장 의존이 생기고, 새 단가 등록이 매번 이전 행 종료일 갱신을 동반해 §17.1의 단일 트랜잭션에 잔가지가 붙는다. ② 겹침 검사를 서비스 코드로: 동시 등록에 뚫린다(§17.4 "코드에서 확인 후 INSERT는 race로 뚫린다").

**되돌리기 비용** — 지금은 테이블 1개와 조회 함수 1개. S3-1의 전표 단가 스냅샷이 이 함수를 소비하기 시작하면 구조 변경이 전표 생성 경로 전체로 번진다.
